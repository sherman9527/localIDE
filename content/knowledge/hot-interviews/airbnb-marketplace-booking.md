# 【Airbnb】预订、库存与价格一致性（市场不出错的那一半）

来源公司：**Airbnb**｜岗位方向：Senior/Staff Backend（Booking / Marketplace / Payments）、Senior Data Engineer（Marketplace Finance / Supply）
对应考点：`airbnb-booking-concurrency`、`airbnb-price-consistency`、`airbnb-marketplace-equilibrium`、`payments-ledger`（交叉）、`idempotency-retry`（交叉）

## 1. 核心机制

### 1.1 库存的本质：日期区间 + 规则，不是"一行 = 一晚"
- 一个 listing 的可订性由**日历 + 规则**决定：最小/最大停留、提前预订窗口、检查入限制、是否开放"灵活日期"、房东手动封档、以及**价格随日期网格变化**（price grid）。
- 冲突判断是"区间重叠 + 规则校验"，不是唯一索引能直接表达；因此常见实现是：
  1. 预检（乐观，展示层用缓存价格与可用性）；
  2. 锁窗口（`listing_id + 日期区间` 的互斥，短 TTL + 版本）；
  3. 创建预订记录并**用唯一约束兜底**（如 `listing_id + date` 的占用表，插入失败即冲突）；
  4. 提交前重算价格（缓存价与下单价可能不同 → 必须显式告知用户并让其确认，不能静默改价）。
- 取消/改期会把库存放回，但要处理"已支付未清算""部分退款""同一区间被新客抢占"的组合状态。

### 1.2 价格一致性（Airbnb 特有的高信任成本问题）
- 展示价链条：搜索页（每晚/总价含费）→ 详情页 → 下单页 → 支付完成。每一级都有独立缓存与失效策略，任一级的重算逻辑不一致就会出现"价格跳变"。
- 2023 年起多地监管/产品政策要求**展示总含税价、去掉隐藏费用**（清洁费并入总价等），后续多地陆续落地（具体时间线需核实）；工程含义：`定价规则服务` 必须单一实现、可版本化，展示与下单调用同一份计算，差异只允许来自"时间推移导致的可用性变化"。
- 税费：按地区/入住时长/身份（商务旅客 VAT）不同；佣金与分账口径要与财务一致；同一 listing 对不同用户（新老客、货币、促销码）价不同 → 缓存键必须含这些维度，否则串价。
- 监控指标：**价格方差**（同一 listing、同一日期、同一参数在 N 次查询中的不同结果数）、"下单价 ≠ 展示价"发生率、价格跳变后的用户流失与投诉率。

### 1.3 市场反馈回路（principal 会被要求讲这个）
- 排序/价格策略改变曝光 → 房东调最小停留/价格 → 供给结构变化 → 指标回到平台。任何"只优化单边"的策略都可能被回路抵消。
- 指标：搜索无结果率、可订率（真实可订而非"看起来可订"）、超卖/无法入住率（最高危体验）、履约失败率、取消原因分布、价格投诉率、供给多样性与新供给成长。
- 实验：双边干扰下用市场级随机化（城市/时间片/集群），或用合成控制/switchback；长周期政策评估用准实验（DID/断点回归）而非 A/B。

### 1.4 风控与信任（预订链路的另一半）
- 欺诈信号：新账户 + 高价预订 + 非常规设备/IP + 收款人聚集（图特征）+ 身份信息不一致；拦截要区分"误杀成本"与"欺诈损失"，且可申诉、可解释。
- 滥用模式：占位不付款（锁库存）、批量探测价格/日历（爬虫）、取消博弈（旺季囤两个日期再退一个）→ 对应机制是"锁窗口配额 + 取消行为画像 + 限流"。
- 与隐私的张力：风控需要数据，平台必须做用途限定与最小化（Airbnb 场景下"房东/房客互相可见的信息范围"是产品与合规边界）。

## 2. 会被追问什么

1. "并发下如何保证不超卖？给出不依赖分布式锁的方案。"（占用表唯一约束 + 冲突即失败 + 意图化下单）
2. "锁窗口用 Redis，进程在锁里挂了会怎样？"（TTL 自动释放 + 悬挂预订对账；锁只是效率手段）
3. "用户看到的价是 3 分钟前的，下单时涨了，你怎么处理？"（显式重算与确认、价格保护策略（小幅容差内锁定）、记录差异并作为一致性指标）
4. "改期怎么保证两边库存都不出错？"（原子换绑：新预订创建成功再释放旧区间，失败回滚；补偿事务与状态机 + 对账）
5. "价格计算逻辑改了，如何安全上线？"（规则版本化 + 影子计算对拍（同一输入新旧实现 diff）+ 分市场灰度 + 财务口径校验）
6. "缓存 key 设计不当导致串价，你怎么发现？"（不变量断言：同参数多次查询结果一致；用户维度差异必须来自"允许的个性化维度"白名单）
7. "超卖发生了 200 单，你怎么止血、怎么找根因、怎么防复发？"（停止相关写路径 → 逐单处置（安置 + 补偿）→ 变更/时间线关联 → 加占用约束与自动检测）
8. "市场策略（给新供给提权）如何评估净收益？"（市场级实验 + 长期指标（房东留存、供给多样性）+ 短期体验护栏 + 仿真预筛）

## 3. 常见错误答案

| 错误 | 为什么不够 senior |
|---|---|
| "用数据库行锁锁住 listing" | listing 级锁把并发压成 1；真实做法是区间粒度 + 唯一约束 + 乐观重试 |
| "先查可订再下单" | 典型 TOCTOU 竞态；必须"写入即判定"（唯一约束/条件写） |
| "Redis 锁保证不超卖" | 锁失效窗口 + 无 fencing；正确性必须落在存储约束 |
| "价格在详情页缓存 5 分钟就好" | 缓存键缺维度导致串价；无一致性监控 |
| "改价直接刷缓存" | 没有影子对拍与财务口径校验，容易出"资损/合规"事故 |
| "超卖就客服道歉" | 没有不变量检测与自动拦截，事故会重演 |
| 按访客随机实验评估供给策略 | 双边干扰，结论不可信 |

## 4. 出题角度

### 题面草稿 A（`code`，`judgeKind=redis`）
> 实现"日期区间锁 + 提交"的最小正确实现（判题在单实例 Redis + 顺序重放并发请求下验证）：
> 1) `try_lock_dates(listing_id, from, to, ttl_sec, req_id)`：同一 listing 的**重叠区间**必须互斥（不重叠可并行）；同一 `req_id` 重入返回成功且续期（幂等）；
> 2) `release(listing_id, from, to, req_id)`：只释放自己持有的（不得误删他人锁）；
> 3) `commit_booking(...)`：要求"锁仍持有"才可提交，提交后自动释放；提交返回 `fencing_token`（单调递增），存储侧（题面用 `booking` key 模拟）拒绝更小的 token；
> 4) TTL 过期后锁可被他人取得，但**已提交**的预订不得被后续操作覆盖（用占用 key + 唯一性验证）。
> 用例：重叠/不相交、并发 200 请求同区间只有一个成功、重入续期、误删他人锁被拒、过期后 takeover、fencing 拒绝旧 token、提交后重复提交幂等返回同一结果。

判分核心：区间重叠判断与"锁不是正确性来源、约束才是"的实现意识。

### 题面草稿 B（`rubric`，10 分制）
> **你正在面试 Airbnb 的 Staff Backend Engineer（Booking Integrity），50 分钟**
> 背景：旺季某城市出现超卖（同一天被两单占用）137 起；同时价格一致性投诉环比 +40%（下单价高于展示价）；工程现状：可订性检查走"搜索服务缓存 + 独立的价格服务"，写路径是"检查 → 创建 → 支付"，无统一不变量监控；法务要求新增"总含税价展示"必须与下单一致；财务要求价格变更可追溯（哪一版规则算出的价）。
> 给出：目标写路径（含库存与价格原子性方案）、缓存与失效设计（价格与可用性分别怎么办）、不变量与监控（怎么在 60 秒内发现新的超卖）、灰度迁移（不停写）、事故处置与根因定位方案、以及"性能 vs 正确性"的一处明确取舍与理由。

**加分点**
1. 写路径以"占用表唯一约束（`listing_id, date`）+ 条件写"为正确性来源，锁/预检只用于降低失败率；说清并发失败的用户体验（重试建议日期、排队、降级）。
2. 价格与库存的耦合讲清：下单时**重算并显式确认**；定义"可容差范围"（如 24h 内小幅波动锁定）与超出时的产品流程；缓存键维度清单（货币、人数、促销、税费口径、用户维度白名单）。
3. 不变量清单可自动检测：区间无重叠占用、总含税价展示=下单（同参数同版本重放）、每笔预订可回溯到"规则版本 + 输入 + 输出"、库存释放与退款状态一致。
4. 监控指标具体：超卖检测（每 5 分钟重放约束检查）、价格方差与跳变率、下单失败原因分布、fencing 拒绝计数；60 秒发现靠"写入即断言"（约束冲突率异常告警）+ 变更关联（部署/规则版本时间线）。
5. 迁移方案分阶段可回滚（双写占用表 → 影子校验 → 灰度按城市/流量切读 → 停旧），并给出每阶段退出判据与回滚触发条件。
6. 事故根因方法：变更时间线 + 并发路径重放（把线上冲突请求在沙箱重演）+ 数据取证（重叠区间分布是否集中在特定 listing/时段/接口版本）。
7. 防复发机制：契约测试（重叠判定用例族）、CI 卡口（禁止"检查后写"模式）、发布闸（冲突率阈值）、以及值班手册与补偿流程（安置成本与用户沟通模板）。
8. 版本与审计：定价规则版本化、影子计算对拍（新旧 diff 率）、财务口径可重放（用历史规则版本重算某笔订单）。
9. 明确取舍：例如"接受下单页多一次重算（+80ms、+5% 失败率）换取超卖归零与合规"，并说明为什么不是"更缓存一点"。
10. 组织面：与法务/财务/客服的接口（谁定义容差、谁批补偿额度）、以及把"不可信的服务边界"写进规范。

**不足点**
- 用"更强的锁/更长 TTL"解决超卖。
- 价格不一致归因给"缓存刷新慢"，不解决维度键与单一实现。
- 无不变量与自动检测（事故靠用户上报）。
- 迁移"一次切换"，无双跑对比与回滚。
- 无规则版本/审计（财务追溯答不出）。
- 不讨论用户体验侧的失败处理（冲突后给什么）。
