## 1. 核心机制

### 1.1 端云分工的设计次序（Apple 面试最想听的思维模型）
1. **能在端上算完的，不出端**（输入法/相册/健康/设备端小模型推理）；
2. 必须出端的，做**数据最小化 + 去标识化**（去掉直接标识符、聚合到可发布粒度、必要时加噪）；
3. 敏感推理需要大模型时，进入**受信任的隔离云端环境**，并要求可验证性（代码/构建设定被审计、透明日志、无持久化用户数据、访问不可由运营人员任意执行）；
4. 全链路都要能回答："这份数据被谁、因何目的、能看多久？"——**用途限定（purpose limitation）是架构属性**，不是文档条款。

### 1.2 三件常用的隐私工具与它们的真实边界
| 技术 | 适合 | 不适合 / 代价 |
|---|---|---|
| 局部差分隐私（LDP，端上加噪后上报） | 计数、比例、直方图、键盘词频类聚合 | 明细级查询、长尾精确值；隐私预算消耗与精度权衡；多轮组合需预算记账（否则通过多次查询把噪声差掉） |
| 中心化 DP（服务端聚合后加噪） | 报表/看板发布、外部可见统计 | 要求"服务端确实拿到了明细"（与最小化冲突）；需可信聚合方；敏感度与噪声标定（Laplace/Gaussian、隐私损失记账） |
| PSI / 隐匿查询（OPRPIR 类） | "我是否在你的集合里"（联系人发现、欺诈名单匹配） | 服务端可通过查询模式反推用户/集合信息（计数与速率侧信道）；工程复杂（算力与延迟）；一旦实现有缺陷就是批量枚举入口 |
- FL（联邦学习）在 2026 的现实：端上训练 + 安全聚合的开销与收益不确定，**"能不能换成端上模型 + 检索"通常更实用**；面试里能质疑 FL 的适用性反而是加分。

### 1.3 端点真实性 ≠ 授权（Apple 后端高频误区）
- DeviceCheck / App Attest 解决"请求来自真实、未越狱设备上的正版 App"，用于**反滥用**（防脚本批量探测、刷券、爬数据）；它**不能**替代鉴权与业务风控。
- Passkey / WebAuthn：抗钓鱼、可跨设备同步，但要有恢复路径（丢失全部设备时的账户恢复流程是真实难点）；服务端要处理"凭证注册/轮换/撤销"与"step-up 二次验证"。
- 典型攻击链（能讲出来就是资深）：用伪造/劫持的 attestation 绕过设备校验 → 批量调用"联系人发现/价格探测/可用性查询"类接口 → 从响应码、计数或时延中侧信道推断 → 形成大规模数据收集。**防线是速率限制 + 批量接口设计（不可枚举）+ 响应统一化 + 异常检测 + 数据侧最小返回**。
- 数据面权限：属性基/关系型授权（用户是否是该资源的参与者）必须落在数据访问层（查询前过滤 + 查询后校验 + 审计留痕），"网关只看 token 有效"远远不够。

### 1.4 删除与可证明性（合规的工程硬指标）
- 删除要覆盖：湖（表快照 + deletion vectors / merge）、OLAP 本地表、缓存与搜索/向量索引、备份与副本、日志（含 trace 里塞进去的 payload —— **最容易漏**）、以及下游派生指标（个体级派生数据）。
- 可证明性：删除工单 + 各层完成回执 + 定期抽查（用哨兵记录验证真的消失）；备份不可即时删除时用"加密索引删除（crypto-shredding）+ 备份保留期承诺"。
- 遥测/事件里的"个体可识别风险"：`device_id` 轮转（防跨期跟踪）、细粒度维度组合可重识别（机型 + 地区 + 时间戳）→ 维度分层泛化 + 小格抑制（k≥阈值才发布）。

### 1.5 推送到端（扇出的隐私与工程交集）
- APNs 类通道的约束（payload 上限、优先级、折叠 id、令牌失效与配额）→ 设计上是"通知不带敏感内容 + 端上再取"（内容可被设备丢失/中间环节暴露时降级影响面）。
- 令牌生命周期：重装/恢复/迁移带来的 token 变更与去重；"设备多副本"下的重复推送控制（collapse-id + 幂等键）。
- 到达率与新鲜度是 SLI；失败与降级的可观测（哪些设备收不到，通常是证书/网络/权限问题）——把端上真实体验接入云端 SLO 是 principal 级答案。

## 2. 会被追问什么

1. "这个分析需求能不能不要个体数据？"（期待主动降粒度；这是 Apple 的核心思维题）
2. "你的差分隐私 epsilon 定多少？为什么？业务能接受多少误差？"（要能给出"误差 vs 隐私"的对话方式，而不是名词）
3. "联系人发现这类接口怎么防批量枚举？"（限流 + 统一响应 + 批量查询的密码学/隐匿方案 + 异常检测 + 最小暴露）
4. "端上传上来的数据里出现 PII（用户自己写的地址），怎么办？"（摄取层检测与丢弃/脱敏、规则可度量、端上提示教育、并审计"谁查询过"）
5. "用户要求删除，你怎么保证 30 天后备份也无效？"（crypto-shredding + 备份生命周期 + 抽查证明）
6. "如果安全团队要求所有请求带设备证明，性能与体验代价是什么？"（校验成本、失败率、老客户端兼容、灰度路径）
7. "服务端模型要读用户内容，你如何架构上保证'不落盘、不访问、可验证'？"（隔离执行环境、无持久化、代码透明性与审计、最小请求上下文、以及"能在端上做就不要上云"）
8. "数据出域/驻留限制如何与检索/AI 功能共存？"（就近计算、只回聚合、路由策略、按数据类型分级放行）

## 3. 常见错误答案

- "匿名化了就安全"（不解释重识别风险与链接攻击，忽略 `device_id` 轮转与组合维度）。
- 把 App Attest 当鉴权（设备可信 ≠ 用户有权）。
- 删除方案只覆盖主表（备份、索引、日志、trace、派生表全漏）。
- "我们加了速率限制"（没有限制对象是什么、如何防分布式慢速枚举、如何检测）。
- DP 只说名词，给不出 epsilon/误差量级与业务沟通方式，也不做预算记账。
- 敏感数据进日志/trace/错误消息（最真实的泄露途径，也是面试杀手）。
- 端云协同只谈"云端更强大"，不谈延迟、离线、成本、隐私预算与失败降级。
- 声称"符合法规"却说不出任何可验证机制（回执、抽查、审计）。

## 4. 出题角度

### 题面草稿 A（`code`，`judgeKind=java-junit`）
> 实现"联系人发现的防枚举服务层逻辑" `ContactDiscovery.evaluate(Request r, RateState st, Clock now)`：
> 输入：`r = {callerId, batchHashes: List<String>（≤500）, attestationOk, tokenScopes}`；`st` 提供该 caller 的历史窗口计数。
> 要求（全部断言）：
> ① **响应统一化**：无论命中与否/是否超配额，返回体大小与字段结构一致（测试断言"命中数与未命中数在响应中不可区分"，即返回 `matchedMask` 恒为固定长度且顺序随机化不可依赖 —— 实现为"返回全部位置但值恒为 `UNKNOWN` 除非二次确认令牌"）；
> ② 批量大小 > 500 或 `attestationOk=false` → 拒绝但返回同样的统一结构（不得泄露"因哪条被拒"）；
> ③ 速率：按 caller 与全局双层预算（令牌桶），超限时返回 `throttled=true` 且 `retryAfterMs` 由桶恢复时间算出（不得固定值）；
> ④ 防慢速枚举：同一 `batchHash` 在窗口内重复出现计入"探测分数"，分数超阈值触发 step-up（要求二次确认）；
> ⑤ 审计：每次调用产出一条 `AuditRecord(callerId, batchDigest, decision, quotaRemainingBucket)`，**不得包含**具体 hash 明文（用摘要）；
> ⑥ 时钟注入下窗口正确（跨边界不重复计数、不出现双倍放行）。
> 用例：正常命中、超批量、无 attestation、限流触发与恢复、慢速枚举检测触发 step-up、审计无明文、跨窗口边界。

（考察点是把"防侧信道"写成可验证的代码行为，而不是概念。）

### 题面草稿 B（`rubric`，10 分制）
> **你正在面试 Apple 的 Senior Software Engineer（iCloud / Privacy-sensitive Services），45 分钟**
> 需求：新功能"跨设备智能搜索"——用户可对自己的照片/备忘录/文件做自然语言查询。约束：① 用户内容不得以可读形式离开设备，除非用户显式同意且进入受证明的隔离云环境；② 服务端不得持有可解密用户内容的长期密钥；③ 索引构建要在低电量/离线场景下可用且不拖慢设备；④ 查询延迟 p95 < 800ms（端上索引命中时），否则回退到云端；⑤ 需支持"账户恢复"与"设备撤销"后旧设备不可再访问。
> 请给出：端云协同架构（索引放哪、模型放哪、查询执行在哪）、密钥与信任边界、回退策略与其隐私代价、性能与电量预算、账户恢复/撤销的安全模型、可观测性（不得泄露内容）、以及"哪些查询你宁可不回答"的判定规则。

**加分点**
1. 默认端上执行（端上 embedding 索引 + 端上检索 + 端上重排），云端仅在显式同意 + 受证明环境 + 端到端加密上下文下参与；明确"回退云端"的触发条件与用户提示。
2. 密钥模型清楚：内容密钥由用户设备持有（E2E），云端只做"不可逆索引/密文检索"或"隔离环境内明文处理"，并说明两种路线的攻防差异与选择理由。
3. 索引构建工程：增量（内容变更事件驱动）、低电量/充电时才做重计算、可中断可恢复、缓存与去重；给出索引体积与设备存储预算。
4. 延迟与成本预算：端上 p95 < 800ms 的达成路径（预计算 + 分层召回 + 小模型端上重排），以及云端回退时的隐私降级说明（只送查询意图/密文向量而非明文）。
5. 账户恢复与撤销：恢复流程的对抗强度（不能变成后门：可信联系人/延迟等待/强度分级）、设备撤销后的密钥不可达保证（rotate + 数据失效）、以及"云端残留数据"的处置与证明。
6. 可观测不泄露内容：指标只记结构与统计（查询长度分桶、命中数、耗时、端/云路径占比），日志/trace 严禁内容片段；错误消息脱敏（这是真实事故源）。
7. "宁可不回答"的规则可执行：涉敏类别（健康/未成年/第三方隐私内容/精确位置）、要求跨用户聚合、批量导出倾向、异常高频探测——统一策略引擎判定并返回可解释的拒绝原因（且不泄露策略细节给攻击者）。
8. 威胁建模有重点：端上恶意 App 读取索引、备份链路、云端环境运营人员、模型供应商旁路；针对 Top 3 给出控制与验证方式。
9. 演进与兼容：端侧模型版本偏斜（多版本索引共存与重建策略）、云端模型升级的回归评测（质量分 + 隐私评测），以及"旧设备不升级时功能降级"。
10. 明确取舍：例如"接受端上索引召回略低于云端集中索引，换取零内容出端"，并说明如何量化损失（离线评测 + 用户可见的"未找到全部结果"提示）。

**不足点**
- 把内容/明文向量直接上云，用"我们会脱敏"糊过。
- 密钥模型含糊（服务端能解密、或"运维不会看"）。
- 无端上资源预算（电量/存储/CPU）与失败路径。
- 账户恢复设计可被社工（短信验证码即通过）。
- 日志里带查询内容（真实高频事故）。
- 无"不回答"策略，或拒绝理由把策略细节泄露出去。
- 无版本偏斜与重建方案（新模型上线即全量重算，成本与体验双爆）。
