## 1. 核心机制（面试里必须能画出来的链路）

### 1.1 数据闭环：从埋点到在线训练，而不是"批训练 + 上线"
```
端上埋点（预置事件 + 自定义事件，控制台先落库 → SDK 再上报）
  → 采集与校验（实时埋点检测 / 事件验收 / 元数据管理里禁用事件或属性）
  → 总线（Topic + 队列 + 位点：MaxOffset / MinOffset / ConsumerOffset）
  → 明细层（湖或 OLAP：ByConity / ClickHouse 类列存）
  → 派生层（事件/留存/漏斗指标、用户分群、行为流）→ 看板与 API 服务
  → 特征与样本（曝光日志 join 行为流；时点必须可复原）
  → 在线训练与在线服务（Monolith：同一框架支持 batch/real-time training and serving）
  → 实验读数（流量层/互斥域 + 多天累计 + 显著性）→ 反哺埋点与口径
```
- **Monolith 的问题陈述是整场面试的锚**：通用深度学习框架"为推荐场景（动态稀疏特征）调优静态参数与稠密计算会损害模型质量"，且"batch-training stage and serving stage completely separated，模型无法实时接受用户反馈"【源 S1】。它的三个答案：① **collisionless embedding table**（无冲突 embedding 表，用"expirable embeddings（可过期）+ frequency filtering（低频过滤）"来压内存）；② "production-ready online training architecture with high fault-tolerance"；③ **"system reliability could be traded-off for real-time learning"**——可靠性是可以拿来换实时性的【源 S1】。仓库 README 同样只写这两点：无冲突 embedding 表保证不同 id 特征的唯一表达、实时训练捕捉热点，并"built on the top of TensorFlow and supports batch/real-time training and serving""Monolith has successfully landed in the BytePlus Recommend product"【源 S2】。
  → senior 必答："**在线训练掉了样本怎么办**""**参数版本与特征版本怎么对齐**""**实时性的收益边界在哪**（论文承认要拿可靠性换，那么换多少、谁承担）"。
- 埋点侧的时点正确性是同一枚硬币：指标要的是"事件发生时间"，在线训练要的是"打分时刻可见的特征值"，两者都要求链路上**同时保留事件时间与到达/落库时间**（这条是【推】，但由"实时埋点检测关注的是数据上传情况"【源 S7】与位点模型【源 S15】可推出落地形态）。

### 1.2 埋点治理：它是一套**元数据工作流**，不是"上报就完事"
火山引擎 DataFinder 文档把埋点治理写成了可执行的产品动作（都是【源 S7】）：
- 对象模型：**事件**（用户动作，"主要通过应用内埋点实现，因此也称为埋点数据"）、**事件属性**（描述事件的信息：设备侧的操作系统/软件版本/渠道/IP，业务侧的视频 ID/名称/分类/标签）、**预置事件与预置属性**（SDK 自带、由系统统一配置上报时机）。
- 生命周期：**元数据管理 → 一般事件**里做"新增事件、编辑事件、设置事件状态、**验收埋点**"；"**一般事件列表仅展示已验收的事件，未验收事件可点击验收事件查看并完成验收**"；权限单独授予（"数据管理-一般事件-可管理"，无权限只能看）；建议"**先查看预置事件是否已满足业务需求，不满足再手动创建自定义事件**"。
- 校验与影响面：**实时埋点检测**（实时检测、快速验证埋点是否正确及数据上传情况，支持 Android/iOS/微信小程序等多端）；**变更历史**（事件级变更日志）与**血缘关系**（图表/看板 + 用户分群，且区分"**直接引用**"与"**间接引用**"，分群血缘还带"最新分群用户数、近 30 天的查询次数"）——文档同时说明这两项属于增值"埋点治理模块"【源 S7】。
- 全埋点 vs 代码埋点的官方取舍【源 S8】：
  - 全埋点优势："部署 SDK 后即会自动且持续地收集…即使最初并未明确指定要分析哪些特定事件…因此可**支持数据回溯**——即可以在任何时候对过去的数据进行查询和分析"；
  - 全埋点劣势（原文列举）："无差别全量采集，产生无效数据上报，**浪费流量/存储/计算资源**""**无法采集业务相关属性**""版本上线后埋点内容迭代灵活性低""对开发框架有一定限制"；
  - 代码埋点的不可替代性："尤其是一些**非点击的、不可视**的行为，非代码埋点实现不可——例如：搜索结果返回、注册结果返回、Banner、楼层、**个性化推荐/千人千面页面**"；
  - 治理动作：**先规划 → 在控制台录入埋点和属性（先落库）→ 集成 SDK 时配置上报 → 打开全埋点开关**；停止采集用"数据管理 > 元数据管理中**禁用对应事件或属性**"或项目中心关全埋点开关，**无需改代码**；"热力图、圈选事件功能需开启全埋点才可使用"。
- 【推】架构结论：埋点是**契约**（名称/属性/上报时机/生效版本/验收人），而"可回溯"决定了"全埋点买的是覆盖，代码埋点买的是语义"，因此成本治理的正确刀法是"**按下游引用量（血缘）下线事件**"，而不是按采集量。

### 1.3 OLAP 与数仓：字节的公开叙事是"ClickHouse 撞墙后存算分离"
ByConity 开源公告给了完整演进【源 S3】：
- 起源："traced back to **2018** when ByteDance initially implemented **ClickHouse for internal use**"；业务增长后 ClickHouse 的 **Shared-Nothing**（各节点独立、不共享存储）架构带来三类痛点：
  1. **扩缩容**：计算与存储紧耦合，"scaling the system incurred higher costs and involved data migration"，做不到实时按需伸缩，资源利用率低；
  2. **多租户/共享集群**：读写在同一节点上执行，"often interfered with each other, impacting overall performance"；
  3. **性能**："support for complex queries, such as **multi-table join** operations, was not optimal"；
- 于是 2020 年内部立项改造，2023 年 1 月 Beta、5 月底开源；架构是**存算分离**（统一的全集群数据管理 + 分布式存储 → **计算节点无状态**），能力清单：弹性伸缩、读写分离、**租户资源隔离**、**读写数据强一致性**，并复用列存、向量化、MPP、查询优化、代码生成、索引、压缩等 OLAP 技术；场景定位为交互式查询、实时看板、实时数仓【源 S3/S4】。
- 第三方落地案例（可用于题面，但注意作者不是字节员工）：MetaApp 用 ByConity **在生产环境全量替换 ClickHouse，使资源成本降低超 50%**；其 OLAP 平台是"离线（DataX 把 Kafka 数据集成到 Hive 数仓，再生成 BI 报表，用 Superset 展示）+ 实时（GoSink→ClickHouse、CnchKafka→ByConity）"双链路，功能包含"事件分析、转化分析、自定义留存、用户分群、行为流分析"，需求里明确要"对小部分人群做 AB 实验"【源 S5】。→ 面试用它来考"**双链路怎么对账、口径谁是一次真相**"，比背引擎参数更有区分度。

### 1.4 分层、口径与治理：DataLeap 把"数仓规范"做成了模块
火山引擎 DataLeap（数据中台）官方模块清单【源 S6】：
- **数据集成**（异构数据源高速稳定同步）、**数据开发**（"**一体化集成批式、流式数据开发能力**"）、**智慧运维**（对发布到生产的任务与实例统一运维监控）、**数据服务**（从数据集快速生成 API 并统一管理发布）；
- **数据地图**："收集和展示**全链路元数据**，帮助数据消费者查找、理解、应用数据"；
- **数据标准**："提供数据标准、标准代码、**命名词典**管理能力，并且将数据标准用于数仓数据表**字段元数据对标**，通过**标准监控统计**推动数仓规范数据建设，**消除数据的不一致性**"；
- **指标平台**："以**维度建模**为理论基础，划分并定义**业务线、指标、数据模型**，支持导入多种数据源构建模型，提供多样指标构建方式，**消除指标二义性，保证指标数据出口一致性**"；
- **数据质量**（"通过数据**探查**、数据**监控**与数据**对比**"）、**数据安全**（权限控制、风险与审计、数据保护）、**SLA 治理**（"**提供 SLA 在线化申报与签署**，并通过多种治理保障措施，协同提高全链路数据质量"）。
- 【推】结论：字节对外可核查的数仓分层证据是"**分层靠标准与对标来强制，不靠文档约定**"（命名词典 + 字段元数据对标 + 标准监控统计），以及"**SLA 是要签署的合同，不是口号**"。ODS/DWD/DWS/ADS 这套命名是行业通用（阿里云文档里才有的官方分层页），**不冒充字节官方**。

### 1.5 实验分流与读数：把"能不能归因"写成机制
火山引擎 A/B 测试（DataTester）文档给了可直接出题的规则集【源 S9】：
- 对象：**流量层**（单层内可按比例把 100% 流量分给多个实验、实验内再分多个实验组）与**互斥域**（可嵌套子互斥域；"选择绑定已创建好的流量层时，不支持绑定已关联实验的流量层"）；
- 约束：**客户端实验只可添加客户端互斥域，服务端实验只可添加服务端互斥域**；"运行中的实验，不支持移除互斥域"；"如果一个互斥域中已有运行中实验，则其他运行中实验不能再加入该互斥域，但可添加草稿箱及调试中的实验"；
- **正交的机理**（官方例子）：两实验各占 100% 且互不处理时，"一个用户被 A1 命中时，同时也会被 B1 命中"→"B1 组指标涨了，真的是 B1 的策略生效了吗？"；解法是把 A1/A2 各切一半分别进 B1/B2，"这种影响也均匀地分布在实验 B 的两个组之中"；实现上"**火山引擎 A/B 测试的分流服务通过两次运算「哈希函数」，使得不同互斥域的流量之间呈正交关系**"；
- **打破正交的特例**："父子实验（dependent experiment）——流量继承：选择某个正在运行的实验作为'父实验'，从中选择某一组，并将新的实验开设在这组流量之下"；
- 组织级评估：互斥域组可有自己的**保留对照组**，还有**全局保留对照组**"评估 3 个部门累加的提升效果，例如评估 APP 的用户生命周期、停留时长、总人均 GMV 这类大盘级业务指标"，并用于"评估各个团队的实际绩效"。
- 读数口径【源 S10/S11】：实验数据统计方式是"**多天累计数据**"——"以进组用户数为例，多天累计的用户数，即是实验期间累计进组并**去重**后的用户数"；官方对三种口径的评价："相比单天累计，多天累计更能保证各组的样本是「**同质可比**」的；相比多天平均，多天累计更易检验出受影响指标的**显著性**，因为多天累计使得实验获得了更多样本，这意味着随着实验的进行，实验的检验灵敏度在不断提高"；**"实验开启当天按实时统计进组人数，开启第二天之后按 T-1 日天级更新，具体口径为截止当天 0 点的实验累计进组人数"**；指标类型分**事件指标 / 留存指标 / 漏斗指标**三类；报告页提供天级趋势图、概率分布图与箱型图，并可下载进组用户 ID（"最多可以下载 500 万条数据"）。
- 样本量与时长【源 S12】：文章标题即痛点——"每次实验需要多少流量""实验时间开多长没有概念"，正文走"总体/样本/统计量 → 抽样分布（标准正态、卡方、t、F）→ 参数估计（点估计与区间估计）→ 置信区间与置信水平"的推导路径，来源标注"**来自字节跳动数据平台 DataTester 团队**"（发布在火山引擎开发者社区，署名"松宝写代码"）。→ 检验灵敏度随样本累积提高 ≠ 可以偷看：**多次窥视读数会抬高假阳性**（这条是【推】，但和"检验灵敏度不断提高 + 需要预注册假设"能直接对上）。
- 实时链路的投递语义是实验与特征的公共底座：集群消费"每条消息仅被消费一次"、广播消费"每条消息会被消费多次"、顺序消息分全局/分区、事务消息保证"最终一致性"、达最大重试次数后落**死信队列**、延迟消息"最长为 3 天或消息保留时长的 3 倍（两者取较小值）"、堆积由 Max/Min/Consumer 三类位点决定【源 S15】。

## 2. 会被追问什么（字节数据风格：先问口径，再问你怎么证明）

1. "在线训练时，一条曝光样本的特征取哪个版本？"（打分时刻可见值 + 特征版本号；否则标签泄漏与离线在线不一致）
2. "你说可靠性可以换实时性，具体牺牲什么？故障后怎么补？"（参数丢失/版本回退、重放窗口、死信与补采；Monolith 的容错与在线训练是同一设计【源 S1】）
3. "无冲突 embedding 表怎么避免 OOM？"（可过期 embedding + 低频过滤是官方给的内存控制手段【源 S1】；追问"过期策略与热 key 复活"）
4. "同一个'人均 GMV'，分析同学和实验平台算出来不一样，谁的错？"（分母与去重域：进组用户"累计去重"【源 S10】vs 活跃用户；指标出口是否走指标平台【源 S6】）
5. "为什么客户端实验和服务端实验不能共用互斥域？"（分流单元不同：设备/用户 ID 口径、哈希域不同，混用会让互斥关系失效【源 S9】）
6. "父子实验为什么危险？"（官方明确"打破正交"，子实验继承父实验的组内流量 ⇒ 结论只能外推到父实验组内人群【源 S9】）
7. "两个互斥域里的实验同时涨，你怎么证明不是互相污染？"（正交性来自两次哈希；再看各组是否均匀、做 SRM/组间均衡性检验，以及全局保留对照组【源 S9/S10】）
8. "埋点要下线一个事件，你的依据是什么？"（血缘：直接/间接引用的图表、看板、用户分群 + 近 30 天查询次数【源 S7】；不依赖"问一圈有没有人用"）
9. "全埋点省钱还是费钱？"（它买的是"可回溯"，代价是流量/存储/计算与"无法采集业务属性"【源 S8】⇒ 分层：骨架事件代码埋点，长尾行为全埋点）
10. "为什么不用一份 OLAP 把明细、看板、排障都塞进去？"（ByConity 的痛点清单就是答案：读写干扰、扩缩容代价、多租户隔离、复杂 join【源 S3】）
11. "离线和实时双链路的差异怎么归因？"（分类为晚到/回补、口径变更、乱序、事件重复；需要一次性真相层与"数据完整度"readiness 门【源 S5 + 推】）
12. "看板 8 点没数，先做什么？"（任务级 SLA + 上游分区完整度；"数据尚未完整"标记 vs 报错；SLA 是签署件【源 S6】）
13. "实验可以每天看一眼、显著就停吗？"（累计口径 + 检验灵敏度不断提高【源 S10】与多次窥视的假阳性膨胀【推】的冲突，正解是固定时长 + 护栏 + 停线规则）
14. "你上线新口径（如剔除某类无效流量），历史怎么办？"（口径版本化、可比区间冻结、重算或截断标注；"消除指标二义性、保证出口一致"是指标平台的职责【源 S6】）

## 3. 常见错误答案（背题型信号）

| 错误 | 暴露点 |
|---|---|
| "特征都存 Redis，越新越好" | 无时点正确性、无版本对齐、无降级读旧值的一致性问题 |
| "在线训练 = 把批训练改成流" | 没意识到通用框架与稀疏动态特征/在线服务的结构冲突【源 S1】 |
| 把 embedding 内存问题当"加机器"问题 | 官方给的是过期 + 低频过滤【源 S1】 |
| "埋点上线后有人反馈不对再改" | 没有验收/变更历史/血缘三件套【源 S7】 |
| 用全埋点采业务属性 | 官方明写"无法采集业务相关属性""非可视行为非代码埋点不可"【源 S8】 |
| 数仓分层只背 ODS/DWD/DWS/ADS | 说不出"命名词典 + 字段元数据对标 + 标准监控"这种强制机制【源 S6】 |

## 5. 出题角度

### 题面草稿 A（`code`，`judgeKind=mysql`）——"同一个指标，四个答案"
> 表：`assignment(exp_id, layer_id, mutex_group_id, user_id, bucket, assigned_at)`（进组流水，同一用户可重复出现）、`event_log(user_id, event_name, event_date, cnt, revenue)`、`exposure(user_id, item_id, ts, model_version)`、`conversion(user_id, ts, gmv, order_id)`、`metric_dict(metric_key, name, business_line, definition)`。
> 要求（口径必须写在注释里，注释也算分）：
> 1) **累计去重进组用户数**：按"实验期间累计进组并去重"定义输出 `users_cum`；同时输出"天级活跃进组用户数" `users_daily_avg`（= 每日去重的平均），并给出两者差值与差异来源；
> 2) **人均 GMV 双分母**：分别以 `users_cum` 与"当日进组且当日有事件的用户"为分母计算实验组/对照组人均 GMV，输出四列 + 差异百分比，并标注哪一个才可用于实验结论（题面要求写出"同质可比"判断）；
> 3) **分流均衡性检测**：给定预设分流比例 `exp_ratio`（从 `metric_dict` 取，`definition` 里含 JSON 比例），计算每个实验各组实际占比与预设的偏离，偏离 > 0.5% 标 `SRM_RISK`；并对"同层多实验"输出各实验组的交集用户数（>0 说明同层被重复占用，违反互斥）；
> 4) **跨层正交性检查**：对任意两层，统计联合分布的边际独立性（每组合占比 vs 两侧占比乘积，最大相对偏差 > 5% 标 `NOT_ORTHOGONAL`）；
> 5) 用 `exposure` 与 `conversion` 还原"最后一次曝光即被成交"的转化率（窗口 24h，同一用户多次曝光取最晚，且必须排除 `model_version` 缺失的曝光记录）。
> 用例：同用户跨天重复进组、同层两实验抢占同一批人、两组比例失衡、跨层分布偏斜、曝光无版本字段、成交早于曝光。
> 区分度：是否把"累计去重"和"日活平均"当成两件事；SRM 与互斥违例是否分开报；正交性检查是否用联合分布而不是"两组均值差不多"。
