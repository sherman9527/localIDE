# 【Apple / Airbnb】行为面 = 技术深挖：追问链、信号与判分设计

来源公司：**Apple + Airbnb**｜岗位方向：全部 senior / principal 方向（数据、后端、平台、AI 平台）
对应考点：`behavioral-deepdive`、`unknown-domain-reasoning`、`incident-story`、`numbers-on-demand`
出题形式：`rubric`，`judgeKind=llm-rubric`（这两家都不问"你多沟通"，而是**抓着简历上的一句话往下挖三层**，直到你要么给出可验证细节、要么承认没做过）

---

## 1. 核心机制：深挖式行为面的结构

### 1.1 一条标准的追问链（面试官视角）
```
"讲一个你最有代表性的系统。"
 → 为什么需要它？（业务问题与量化目标，不是技术流行词）
   → 你的具体决策是什么？哪些是你做的、哪些是团队做的？（拆个人贡献）
     → 备选方案是什么？为什么否掉？（技术判断力的核心证据）
       → 数字：规模、延迟、成本、错误率、改进前后（肌肉记忆测试）
         → 哪里出过错？怎么发现的？（自动检测 vs 用户上报）
           → 事后你改了什么机制？（复盘是否落地为卡口）
             → 如果重做，你会怎么做？（自我认知与成长信号）
               → 你如何让别人跟你一起做？（影响力：RFC、工具、指标）
```
principal 级会额外问：**"你决定不做什么"**、**"你改变了团队的什么习惯"**、**"你培养/带动过谁"**、**"你与算法/财务/法务冲突时怎么定夺"**。

### 1.2 两家的风格差异（据公开经验帖概括，个人轮次会有差异）
- **Apple**：更"内向深挖"——把你负责的那一小块问到底层（为什么这个数据结构、这一层为什么延迟高、这个 API 为什么这么定）；重视 ownership、对细节与用户体验的执着、跨组织推动（Apple 平台团队常需"没有直接权力却推动多个 BU"）；对"规模数字"和"稳定性事故处理"要求具体。
- **Airbnb**：更"故事 + 影响"——要求你讲清楚"事情怎么从模糊变清晰"（需求含糊时你如何对齐口径与优先级）、跨职能协作（PM/DS/Legal）、以及对用户/房东双边影响的理解；复盘文化强，坦率承认失败被视为加分；重视"你在没做过的事上怎么学"。
- 共同：都会用"连续为什么"测试你的**真实参与度**；含糊的"我们"（而不是"我"）、没有数字、没有失败、没有反证，都会被继续追问。

### 1.3 判分要点（本项目 `llm-rubric` 的设计依据）
好的深挖回答必须含**四类可核对物**：
1. 数字（量级 + 口径 + 改进前后），
2. 决策与替代方案（为什么不是另一个），
3. 失败与返工（含发现方式），
4. 机制化沉淀（卡口/工具/流程，而不是"我以后更小心"）。
判分时对以下情形扣分：只谈结果不谈过程；把团队成果说成个人；"我们用了 X 所以没问题"；没有任何数字；声称系统完美无缺陷；把复盘写成"加强监控"。

## 2. 高频真题方向（按公司标注，可直接作为题面骨架）

**Airbnb（数据/后端方向常见）**
1. "讲一次你发现并修复的数据正确性问题——你是怎么发现的？"（期待：不变量/对账自动发现 vs 业务方投诉；修复与防复发机制）
2. "两个业务方对同一指标口径争执不下，你怎么处理？"（期待：语义层单点定义 + 影响分析 + 决策记录 + 历史重算/截断的选择）
3. "你做过最 risky 的一次上线/迁移是什么？回滚预案是什么？"（期待：分阶段、双跑、判据、真实事故或"没出事但侥幸"的反思）
4. "描述一次你与数据科学/产品/法务合作，最后你改变了他们的想法（或被改变）。"（期待：证据 + 换位 + 结果）
5. "你的实时管道 SLA 是多少？哪次没达到，为什么？"（期待：分位数新鲜度指标、根因、容量或上游依赖问题）

**Apple（数据/后端方向常见）**
6. "介绍一个你处理过的最大规模数据集：每天多少、成本多少、你怎么把它变快 10 倍。"（期待：瓶颈定位与量化，而不是参数清单）
7. "讲一次线上事故的完整时间线：从告警到恢复，你在每个阶段做了什么。"（期待：MTTA/MTTR、决策依据、止血与根治分开）
8. "你的系统里哪些数据是敏感的？架构上如何保证不被误用？"（期待：分级、最小化、权限落点、审计与抽查）
9. "客户端团队不愿改，但你必须改数据契约，你怎么办？"（期待：兼容策略、灰度、遥测说服、跨团队机制）
10. "你如何在'端上'和'云上'之间划分计算？给一个你做过的例子和量化收益。"（期待：延迟、电量、隐私、成本四要素）

**两家通用**
11. "你没做过 X（新表格式 / 向量检索 / Flink），一周内交付方案，你会怎么做？"（考学习方法与"敢说不确定"）
12. "讲一次你主动放弃/砍掉的功能或重构，为什么？"（principal 强信号）
13. "你的技术债清单如何与业务优先级竞争？"（期待：可量化、偿还机制、真实案例）
14. "你带过人吗？举一个你把某人从'不会'带到'能 owner 一块系统'的例子。"（senior→principal 分水岭）

## 3. 常见错误答案（失败模式与判分别名锚点）

| 模式 | 具体表现 | 为什么被扣分 |
|---|---|---|
| STAR 模板但无技术细节 | 情境/任务/结果都有，动作层全是形容词（"加强沟通"、"深入排查"） | 无法验证你真的做过 |
| 集体主语 | 整段"我们"，问"哪部分是你做的"就卡住 | 参与度存疑 |
| 无数字 | 问规模/成本/延迟只能给"很大、挺慢的" | senior/principal 必须有量级感 |
| 完美故事 | 没有失败、没有返工、没有反悔 | 说明要么没做难事，要么不复盘 |
| 技术名词堆砌 | 说出 Iceberg/Flink/向量库/多 agent 但讲不出为什么不是替代方案 | 判定为背题 |
| 复盘无沉淀 | "后来我们加了监控"（无规则名、无卡口、无自动化） | 事故会重演 |
| 归因外化 | 全是"上游不配合"、"产品乱提需求" | 影响力/Ownership 负分 |
| 编造版本号/指标 | 说"Spark 4.3 的某某特性"（不存在）或"我们 p99 3 毫秒" | 直接判不诚信；本类题应鼓励"不知道就说不知道" |

## 4. 出题角度（本类别特有：题面要自带追问链）

每题由 1 个主问 + 3–4 个**预埋追问**组成，答题者按顺序作答；判分器（`llm-rubric`）对每个追问有独立加分/扣分锚点。

### 题面草稿 A（`rubric`，10 分制｜Airbnb · Senior Data Engineer）
> 主问：**讲一次你发现的"数字错了但没人报错"的数据问题。**
> 追问 1：你是怎么发现的？（若答"业务方反馈"，继续问"现在还有这类风险吗？你做了什么让它下次自动发现？"）
> 追问 2：影响的下游有哪些（表/看板/模型/对外）？你怎么界定影响范围与通知谁？
> 追问 3：修历史数据吗？重算还是截断？谁批准？
> 追问 4：这件事之后你加的具体规则/卡口是什么（给规则名与阈值来源）？误报率如何？
> 追问 5：如果同样的问题今天再发生一次，会是什么原因？（考系统是否有回归能力）

**加分点（每条 +1～+2，封顶 10）**
1. 说清"静默错误"的技术根因类型（不可加上卷、时点 join 用当前维、单位/时区漂移、`max(updated_at)` 丢删除、重复事件被 join 放大）之一，且具体到字段与代码位置级别。
2. 发现方式含**自动化**成分（不变量断言、双路径对账、分布漂移检测），或诚实承认"当时靠人发现，之后我补了 X"。
3. 有量级：影响多少行/多少报表/多少用户可见数字/持续多久（精确或给区间）。
4. 影响面来自血缘（列级/表级），并能说明通知机制（自动生成影响清单，不靠群里 @）。
5. 历史处置有明确决策规则（财务/合规口径不可重算只能截断 + 标注；分析口径重算 + 冻结窗口），并说明由谁拍板。
6. 修复的幂等性与可重跑细节（分区覆盖、双跑对账判据、回滚点）。
7. 沉淀为可执行卡口（规则名 + 阈值推导方法 + 阻塞/隔离/观察分级 + 误报治理），而非"加监控"。
8. 承认误报/规则被关闭的权衡，并说明你如何维持规则可信度（误报率纳入指标、季度清理）。
9. 反思个人责任（为什么当时评审没发现：缺 golden dataset？缺口径签字？缺双路径校验？）。
10. 第 5 问能给出"下一次复发的可能原因"（组织流程漏洞、新数据源未纳管），说明系统性思维。

**不足点**
- 全程无数字、无字段级细节。
- 只说"改了 SQL / 重刷了数据"。
- 影响范围靠"我逐个问下游"。
- 修复方式不可重跑（跑一半失败留下脏分区）。
- 复盘产出是"以后仔细 review"。
- 把责任全推给上游团队。
- 编造不存在的功能/版本号（触发直接低分并要求自证）。

### 题面草稿 B（`rubric`，10 分制｜Apple · Principal Backend / Data）
> 主问：**挑一个你 owner 的系统，给我它的三个数字：日均数据量（或 QPS）、p95 端到端延迟、月度成本，并解释每个数字为什么是这个值。**
> 追问 1：这三个数字里，哪个最容易被"优化动作"悄悄变差？你用什么防止？
> 追问 2：讲一次这个系统的 P1 事故：从第一次异常信号到恢复的时间线，以及你个人的关键决策点（哪些做对了，哪些晚了）。
> 追问 3：这个系统里你**主动砍掉**或**拒绝实现**的是什么？理由与代价？
> 追问 4：如果预算砍 40% 而 SLO 不变，你的动作顺序是什么？哪一步你会明确说"做不到"？
> 追问 5：你在这个系统上留给团队的"非你不可"的东西是什么（机制/工具/文档/人）？

**加分点**
1. 三个数字之间有自洽的推导关系（能现场从流量/事件量反推到成本量级），而不是孤立记忆。
2. 主动给出口径定义（延迟是端到端还是服务端？成本含不含人力/托管费？），并说明口径争议如何处理。
3. 第一个追问指向"静默劣化"防线（尾部采样保失败、步数/膨胀指标、成本与延迟分布右移告警、回归基线）。
4. 事故时间线含 MTTA/MTTR 分段与判断依据（如何区分"变更引发"与"容量引发"），并诚实承认某个决策偏晚。
5. 砍掉的功能有量化理由（使用率、维护成本、与隐私原则冲突），而不是"没时间"。
6. 预算削减动作按 ROI 排序且有风险说明（如降低保留期会影响可回溯性、去掉某冗余会影响恢复时间），并能指出"做不到"的边界（SLO 与成本的硬冲突）。
7. 组织沉淀具体：把某类错误变成 CI 卡口/工具默认值/lint 规则（"让别人写不出错的代码"），而不是文档。
8. 提到跨团队推动的真实阻力与机制（RFC、指标共担、给对方便利）。
9. 对隐私/合规有默认意识（数据最小化、个体级数据非必要不采）。
10. 全程可验证：能指出"这条指标在哪个看板、这个决策在哪份 RFC"（本项目判分器据此评"具体性"，不要求真实外部链接）。

**不足点**
- 报不出数字，或数字之间明显矛盾（QPS × 平均包体 ≠ 带宽/存储量级）。
- 把团队决策全说成个人英雄叙事，或相反"都是领导的决定"。
- 事故只讲"恢复了"，没有时间线与判断依据。
- 没有"拒绝做什么"的能力（principal 关键缺陷）。
- 降本只说"换更便宜的机器/模型"，无风险与二阶效应。
- 声称系统从未出过问题。

### 题面草稿 C（`rubric`，10 分钟｜两家通用，"陌生领域推理"）
> 主问："假设明天你要 owner 一条用 Flink 2.x + Paimon 主键表的实时管道，但你过去只做 Spark 批。给我你前 5 个工作日的计划：读什么、测什么、拉谁、以及你**不知道**的东西列出来。"
> **加分点**：先定义"什么叫跑通"（正确性判据 + 新鲜度 + 成本）；明确"需要核实"的具体清单（2.x 状态与 savepoint 兼容性、Paimon changelog 生产者语义、compaction 与写反压）；安排双跑对账；找对该领域 owner（流平台/表格式维护方）问的 3 个具体问题；提出最小风险的第一步（只读旁路，不动生产 sink）；坦白知识边界而非编造参数名。
> **不足点**：直接给"我一周能学会"式的表态；把批处理经验无条件套用（不知道 watermark/状态/回撤流差异）；不定义验证判据；编造配置项/版本特性。

## 5. 对标 JD 能力项

| 公司 | 岗位方向 | JD 能力项（这类行为题实际在考什么） |
|---|---|---|
| Apple | 全部 Senior/Principal（数据/后端/平台） | "Demonstrated ownership end-to-end"; "Track record of shipping at scale with measurable outcomes"; "Influence across organizations without direct authority"; "Attention to detail and user trust" |
| Airbnb | 全部 Senior/Staff（数据/后端） | "Bias for action with data-driven decisions"; "Candid, feedback-oriented communication"; "Cross-functional partnership (Product, DS, Legal)"; "Mission & values alignment with measurable impact" |

> 入库要求：本类别每题 `source.company` 必填（Apple / Airbnb / 两者交叉），`difficulty` 设 `senior` 或 `principal`，`rubric.points` 中的每条"加分点"必须能对应答题文本中的可验证片段（数字、字段名、机制名、时间线），避免"文笔分"。
