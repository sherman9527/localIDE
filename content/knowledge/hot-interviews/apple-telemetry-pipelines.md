## 1. 核心机制

### 1.1 数据从哪里来：端上优先的管道设计
- 端侧特征：带宽、电量、蜂窝/ Wi‑Fi、后台任务窗口、用户可能随时关机 → **上传是尽力而为、批量化、可丢弃低优先级**的，与云端"事件即达"的假设完全不同。
- 关键设计点：
  1. **采样在端上做还是在云上做**：端上采样省带宽但**不可重算**（没采到的永远没了）；云端全量后采样成本高但可重算、可分层。折中：全量结构化"骨架事件"（小体积、高价值）+ 明细按类别/用户哈希采样上报，并把采样率作为数据字段随行（可还原权重）。
  2. 采样权重不可忽略：任何"按事件数聚合"的指标都必须 `× 1/sample_rate`，否则功能渗透率会算错——这是高频追问点。
  3. 端上时钟不可信：本地时区、用户改时间、NTP 未同步 → 必须同时携带 `device_ts` 与 `server_recv_ts`，口径明确"业务时间用哪个、延迟用哪个测量"。
  4. 乱序与迟到：以"天"为单位重算窗口（滚动 N 天），而不是"到了就写、写死不再改"；迟到数据要可解释（重传、批量补传、离线设备开机）。
  5. 隐私开关与一致性：用户关闭分析共享后，链路上游（端上、网关、湖）都要停止接收与保留；这类"停止"需要可验证。

### 1.2 版本偏斜：数据契约的最大难点
- 客户端不可强制升级 → 同一事件存在 3–5 个 schema 版本共存，字段语义漂移（改名、单位从"米"改"英尺"、时区从本地改 UTC、枚举新增）都是**静默错误**来源。
- 防线：
  - 事件注册表（每事件每版本的字段、类型、单位、时区、生效起止、owner）；
  - 摄取层做"版本路由 + 归一化"（下游只见规范层，永远不直接读 raw 版本）；
  - 漂移检测（枚举分布突变、数值分布 KS/PSI 突变、单位错误会被"数量级 3.28 倍偏移"这类特征抓到）；
  - 契约测试（新版本 SDK 发布前，用真实样本回放跑校验，并把"新增字段的填充率"作为发布闸）。
- 回填与重算：schema 归一化逻辑变化会影响历史（是否重刷？），必须按"口径变更协议"决定（重算 vs 截断 + 标注），且重算需要可重现输入（快照 + 版本）。

### 1.3 处理层：为什么"规模够大就会撞上 shuffle 与成本"
- 遥测类作业的典型形态：宽表 + 高基数维度（`device_id`）+ 时间窗口聚合 + 频繁 join 维度（机型/OS/地区）。瓶颈常是：
  - shuffle 写读与倾斜（按 `device_id` 聚合天然均匀，但按 `app_version`/`model` 聚合会倾斜；null/默认值桶最危险）；
  - 小文件与元数据（每分钟 checkpoint 写出 → 数百万文件；要么调 checkpoint 间隔，要么写入前合并、要么靠表格式 compaction）；
  - 重复处理（回填与日常共用逻辑、幂等覆盖）；
  - 成本（扫描字节 × 作业数；无用列、无分区裁剪的 ad-hoc 查询是主要浪费）。
- 平台侧解法（principal 期待看到）：ESS/远端 shuffle 与动态资源分配的匹配、Magnet 类元数据外置、作业倾斜自动体检与卡口、列裁剪与分区裁剪的 lint 检查、按团队的扫描量配额与归因看板。
- 引擎现实（2026）：Spark 3.5.x 长尾 + 4.1/4.2 试点并存；4.x 的关键变化（ANSI 默认、VARIANT GA（4.1）、Arrow 原生 Python UDF（4.1/4.2）、`CHANGES`/Auto CDC（4.2）、geospatial（4.2）、流式 RTM）需要在升级验证矩阵里逐条覆盖；湖仓侧 Iceberg v3（row lineage / deletion vectors，1.10.0 起）与 Paimon（主键表/LSM）在"可回溯 + 点改"上的取舍是常见讨论题。

### 1.4 存储与查询分层
- 明细（原始/规范层）留在湖（对象存储 + 表格式，冷热分层 + 生命周期）；
- 服务层（看板、API、排障检索）进 OLAP，排序键按真实查询模式设计（`device_id + ts` 服务排障点查；`date + app_version + metric` 服务趋势聚合）；
- 高基数明细不要塞进全文检索集群（成本失控）；日志/事件的模糊查询用列式 + 文本索引（ClickHouse 26.x 已提供含中日文分词的文本索引，能力细节需核实）；
- 每条链路要有"新鲜度分位数 + 完整性对账"（端上发送数 vs 网关接收数 vs 落库数）——**丢包率本身就是一个被产品看的指标**。

## 2. 会被追问什么（Apple 风格：把数字问穿）

1. "每天多少事件、多少 TB、多少成本？p99 事件延迟多少？丢包率多少？"（答不出量级会直接压低评级）
2. "端上采样率和权重字段谁负责？你怎么防止分析师忘记加权？"（规范层视图默认加权 + 裸表权限收紧 + 报表口径校验）
3. "OS 发布后第一天，你的作业怎么不变慢？"（新版本维度爆增导致的倾斜/基数突变、预热、维表版本化、资源弹性与优先级）
4. "一个字段单位从 MB 改成 GB，你怎么在设计上先防住？"（带单位后缀 + 注册表校验 + 数量级漂移检测 + 契约测试）
5. "为什么这条链路不用 Kafka 直连？"（端上不稳定、批量上传、去重、乱序；对比"网关 + 总线 + 流处理"与"批量文件落地"的成本与新鲜度）
6. "PB 级表你怎么做回填？重跑一周需要多久、多少钱、风险是什么？"（分区并行 + 幂等覆盖 + 配额隔离 + 与在线错峰 + 对账放行）
7. "你怎么在隐私约束下做功能使用分析？"（不采集可识别信息、端上聚合、最小化、DP 加噪用于计数/直方图、审计与用途限定）
8. "如果让你把这套管道成本降 30%，你动哪三刀？"（去重复物化、压缩与编码/列裁剪、分区与生命周期、作业合并与小文件治理、查询并发治理——要能量化）

## 3. 常见错误答案

| 错误 | 暴露点 |
|---|---|
| "全量事件都不采样存两年" | 没有成本概念（遥测明细的存储/查询账会爆） |
| 采样不带权重字段 | 指标系统性偏差，且不可事后修正 |
| 用 `updated_at` 做增量 / 用 `insert_time` 当业务时间 | 丢删除与时区/迟到问题 |
| 端上时钟可信 | 数据出现"未来时间"、跨天归属错乱 |
| 每分钟 checkpoint 写出且不治理小文件 | 元数据/listing 成本失控 |
| 认为"schema registry 就能防语义漂移" | 类型兼容 ≠ 语义兼容（单位、时区、枚举含义） |
| 一切塞进一个 OLAP/一个搜索引擎 | 查询形态混合导致互相拖累 |
| 隐私"上线后再补" | Apple 场景里等于架构重做（端上/网关/湖三处都要改） |

## 4. 出题角度

### 题面草稿 A（`code`，`judgeKind=pyspark`）
> **加权采样还原 + 迟到窗口重算**
> 输入 `events(device_id, event_name, app_version, ts, size_bytes, sample_rate)`，`sample_rate ∈ {1.0, 0.1, 0.01}`；另有 `late_batch`（同一 schema，`ts` 落在已处理窗口内）。
> 实现 `daily_metrics(events, late_batch, target_day) -> DataFrame`，输出 `(event_name, app_version, est_events, est_devices, p95_size_bytes)`：
> ① `est_events = Σ(1/sample_rate)`（采样权重还原；`sample_rate<=0` 或 null 视为 1.0 且计入 `anomaly_rows`（题面要求输出为额外一列））；
> ② `est_devices` 为**按权重还原的设备数估计**：设备多次上报时按"该设备该 (event_name,app_version) 的最大权重"计一次（不可简单 sum 或 distinct）；
> ③ `p95_size_bytes` 用**加权样本的分位数**（按 `size_bytes` 升序累计权重，取首个 ≥0.95×总权重的值；禁止 `collect`）；
> ④ `target_day` 判定用 `ts` 且必须按 **UTC**；迟到数据必须并入结果且幂等（对同一输入重复执行两次结果一致）。
> 用例：混合采样率、null/0 采样率、设备跨版本、p95 tie、迟到批次、二次运行幂等断言。

这题几乎无法靠背 API 通过：②③需要真正理解"采样 + 去重 + 分位数"的组合语义。

### 题面草稿 B（`rubric`，10 分制，Apple 风格设计题）
> **你正在面试 Apple 的 Principal Data Engineer（Device Telemetry Platform），50 分钟**
> 规模与约束：20 亿活跃设备；峰值每秒 600 万条上传请求（端上批量、重试导致重复）；日均接收 3.2 万亿条事件、压缩后 450 TB/天；热存 30 天、冷存 2 年（合规要求可证明删除）；隐私要求"不得采集可识别用户身份的数据，且 90% 的分析需求不需要个体级数据"；SLA：核心指标看板 T+1 早上 8 点、排障查询（按设备 + 时间窗）p95 < 3s。
> 给出：端到端架构（端上策略 → 接入与去重 → 总线 → 规范层与派生层 → 查询服务层）、采样与权重治理、版本偏斜与语义漂移防线、去重策略（`event_id` 重复 vs 内容重复的差别，以及内存/状态成本）、成本模型（各层量级 + 三刀降本及其风险）、隐私与删除可证明性、故障模式与降级（重放洪峰、OS 发布日、上游延迟）、以及三条你会定给全平台的硬规范。

**加分点**
1. 端上策略成体系：优先级分级（可丢 vs 不可丢）、批处理与退避、指数抖动、本地缓冲上限与丢弃策略、以及"哪些聚合可以在端上做（差分隐私加噪）"。
2. 去重分层：网关层按 `upload_id`（幂等）、流层按 `event_id`（有状态窗口去重 + 状态成本估算）、批层按内容键（`hash(device, event, ts, payload)`）做兜底；讲清"重复来自哪里 + 各层保留窗口多久 + 状态内存代价"。
3. 采样治理：权重随行、规范层视图默认加权、禁止分析师直连裸采样表（权限与工具双管）、"渗透率/占比类指标必须同一采样域内计算"的规范。
4. 版本偏斜防线具体：事件注册表（含单位/时区/枚举语义与生效区间）、摄取层版本路由与归一化、漂移检测（数量级/分布/KS 与突变规则）、SDK 发布前回放契约测试与填充率闸。
5. 分层与新鲜度：raw（不可变、短保留、高压缩）→ canonical（归一化、加权、长期）→ derived（聚合/指标中间态）；每层有 SLA 与对账（接收数 vs 落库数 vs 派生数）与"可重算窗口"。
6. 查询服务化：排障点查用 `device_id + ts` 排序键与服务层（OLAP 或 KV + 湖直读的组合）；看板走预聚合 + 语义层；明确"为什么不在明细上做 ad-hoc"，以及配额与并发治理。
7. 成本有量级与三刀：例如"列裁剪 + 编码（低基数字典化）降扫描量"、"冷热分层与保留期分级（派生层长留、raw 短留）"、"小文件与 compaction 预算 + 回填与在线错峰"，并给出可测的量化方式与风险（重算窗口变短、排障能力受损）。
8. 隐私可证明：数据分级与最小化在摄取层强制执行、PII 检测（端上 + 网关双层）、删除请求的级联（湖快照/OLAP 本地表/备份/索引）与删除报告（保留期承诺 + 抽查审计），并说明"聚合层为何无需个体数据"。
9. 故障模式：OS 发布日（维度基数突变 + 倾斜）、重放洪峰（限流 + 优先级 + 丢弃策略）、上游延迟（看板用"数据尚未完整"标记而非报错）、时钟/时区事故；每类有自动检测与预案。
10. 三条硬规范可执行且能在 CI/网关拦截（例如："所有事件必须带 `event_id + schema_version + unit` 且注册表校验通过，否则网关拒收"；"所有对外指标必须来自语义层"；"所有回填必须走幂等覆盖 + 对账放行"）。

**不足点**
- 只有"Kafka + Spark + 数仓"三件套图，无去重/采样/漂移/成本细节。
- 采样不带权重或让分析师自行处理。
- 删除合规只说"我们有权限系统"。
- 无降级（OS 发布日与重放洪峰直接压垮管道）。
- 成本没有量级与测量方法。
- 隐私当作事后加固项。
- 讲不清"个体级数据"的必要性与替代方案（这是 Apple 面试的核心考点）。

### 题面草稿 C（`rubric`，短题，10 分钟）
> "一条按小时跑的作业，某天 03:00 分区数据只到 12%（上游网络事故），04:00 补齐。你的看板和下游指标会发生什么？给出至少三种错误表现与对应防线。"
> 期望：不完整数据被当真值（小时趋势假摔）、去重/窗口聚合结果永久偏差（分区 overwrite 未生效、幂等缺失）、下游派生表按"到达时间"而非事件时间归窗（补齐后跨天口径变化）、告警风暴（波动阈值按绝对量误报）、放行判据缺失（缺"数据完整度"字段与 readiness 门）、以及回填后对账与自动重跑的机制。
