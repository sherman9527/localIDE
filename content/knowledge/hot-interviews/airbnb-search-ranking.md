## 1. 核心机制（面试里必须能画出来的链路）

```
查询理解（地点解析/日期/人数/意图/改写）
  → 约束过滤（可用性、最低要求、政策、黑名单）
  → 多路召回（倒排+地理网格 / 向量 embedding / 个性化行为 / 供给策略）
  → 融合去重（RRF 类）→ 粗排（轻量模型，万级→千级）
  → 精排（LTR/深度模型，千级→百级）
  → 重排与产品规则（多样性/打散、新供给曝光、安全与合规、无结果兜底）
  → 结果页价格与可用性填充（price grid / 日历缓存）
```
- **延迟预算是硬约束**：端到端 p95 常落在 200–500ms 量级（自报数字会被追问），其中"结果页价格与可用性填充"往往是最贵的一段——它决定了为什么需要 price grid 与预计算。
- **时点正确性**：特征必须用"查询时刻可见"的值（价格、剩余可订天数、房东近期回复率）；用未来值 = 离线指标虚高、上线掉点，且难以归因。
- **目标定义**：`book the last viewed listing`（KDD'18）这类代理目标的代价：把"搜索会话内的成交"当目标会惩罚"多次会话比较"，也会给头部供给加成 → 需要引入长期指标（复购、取消率、评价分、双边满意度）。
- **双边市场特殊性**：曝光改变供给方行为（房东调价/改最小停留天数）→ 存在反馈回路与跨边干扰，实验单元不能只是"访客"。

## 2. 会被追问什么（按 Airbnb 风格：一条链问到答不出）

1. "你的召回为什么需要向量路？哪类 query 它救回来了，给出量化占比。"（期待具体类别：模糊意图、无关键词、跨语言、"海边度假"式抽象词）
2. "embedding 模型升级，怎么上线？"（双索引/双塔并跑 + 离线 recall/nDCG + 线上小流量灰度 + 老索引保留期 + 回滚判据）
3. "新 listing 没有行为数据怎么办？"（冷启特征：属性/图片/房东历史/位置先验；曝光扶持与"探索预算"，且要能说清对短期指标的牺牲与长期供给价值）
4. "搜索无结果率怎么定义、怎么降？"（约束松开的策略层级、地理放宽、日期弹性推荐、以及"无结果但给了替代"的体验指标）
5. "离线 AUC 涨了 1.5 个点，线上订单没动。你怎么排查？"（分层：数据（特征分布漂移/缺失）、目标错位（代理指标）、系统（延迟导致的截断）、市场（供给被挤占、跨边干扰）、实验（SRM、口径变更、季节性））
6. "特征新鲜度和一致性怎么保证？离线回填与在线特征服务不一致时如何发现？"（同一份定义双路生成 + 采样对比 + 差异告警 + 时点 join 校验）
7. "价格与可用性怎么在结果页不出错？"（price grid 缓存、失效事件驱动、下单时重算与"价格变化提示"，以及一致性监控指标）
8. "你如何做实验？双边市场的实验单元与干扰怎么处理？"（按市场切片/时间片切换、switchback、集群随机化、供给侧实验与需求侧实验分开；SRM 监控与自动停线）
9. "LLM/agent 能进搜索吗？在哪一层？"（查询理解/意图改写/结构化抽取可用；不进入排序打分主链路——延迟、成本、可评测性；需要防注入与可解释留痕）

## 3. 常见错误答案（背题型信号）

| 错误 | 暴露点 |
|---|---|
| "用双塔 + ANN + rerank 就行了" | 说不出约束过滤与 ANN 的执行顺序、预过滤精度损失、延迟预算分解 |
| "离线指标涨了线上一定会涨" | 不懂代理指标与长期目标冲突、不懂市场反馈回路 |
| "特征都存 Redis，越新越好" | 没有时点正确性与训练-服务偏斜概念 |
| "全量重刷 embedding" | 无成本/无灰度/无回滚，不知道索引重建期间查询降级 |
| "按访客随机做 A/B" | 双边市场跨边干扰（SUTVA 违背），switchback/集群随机化不知道 |
| 不知道"搜索无结果""无供给日期"这类产品边界 | 没做过真实搜索系统 |
| 只讲模型不讲延迟/成本/故障降级 | senior 与"调参工程师"的分界 |

## 4. 出题角度

### 题面草稿 A（`rubric`，10 分制，主推）
> **你正在面试 Airbnb 的 Senior Data Engineer（Search & Discovery），45 分钟**
> 需求：为"目的地发现"改版提供数据与排序支撑。现状：搜索 p95 420ms（其中价格与可用性填充占 180ms）；新供给（上架 <7 天）占比 6% 但只拿到 1.2% 曝光；无结果率 7%；离线排序模型 AUC +0.012 的改动上线后订单量 -0.4%（不显著）；数据侧问题：特征回填与在线服务不一致的历史投诉 3 起/月。
> 请给出：① 端到端链路与延迟预算重分配；② 新供给曝光策略与其指标体系（含对短期成交的影响预估方法）；③ 特征一致性与新鲜度的工程解法与验证；④ 那个"AUC 涨、订单跌"的完整归因方案；⑤ 实验设计（含双边干扰处理）与放行/停线判据；⑥ 你会砍掉的一项已有复杂度（并说明依据）。

**加分点**
1. 延迟预算有分解与重分配方案（如价格填充预计算化/网格化、并行调用、缓存与降级返回"稍后价格"并标记），并给出各段目标数字。
2. 新供给策略有机制设计意识：探索预算（有限且可度量）、按质量信号动态退出、避免"扶持导致长期体验下降"；给出可衡量的双边指标（供给多样性、卖家留存）。
3. 特征一致性给出可验证方案：同一份定义双路生成、采样对拍（差异率阈值）、时点 join 正确性用例、上线前"未来信息检查"自动化（标签泄漏检测）。
4. "AUC 涨订单跌"归因分层且可执行：先查数据与特征漂移（分布对比 + 缺失率），再查离线-在线一致性（线上打分复算），再查目标错位（用代理指标拆解：点击涨但成交率跌 → 详情/价格页流失），最后查实验有效性（SRM、样本量、季节性、口径变更）。
5. 实验设计：市场切片随机化/switchback、跨边干扰处理、最小可检测效应与所需样本量计算、预注册假设与护栏指标（取消率、价格投诉、无结果率）、自动停线条件。
6. 无结果率的解法分"约束松开层级"与"供给缺失"两类，分别给产品与技术处置（含替代推荐的排序安全边界）。
7. 明确 embedding/索引升级流程：双索引、影子查询、灰度指标（相关性代理 + 延迟 + 成本）、回滚点与保留期。
8. 数据成本与运维：排序日志/特征快照的存储与生命周期、离在线双份存储的一致性监控、查询回放工具。
9. "砍掉的复杂度"有数据支撑（例如停用某条重复召回路：占 6% 召回但 0.1% 成交贡献，换来 40ms 与 15% 运维成本）。
10. 表达上主动给数字与判据（这是 principal 的关键信号），并说明哪些数字是假设、怎么验证。

**不足点**
- 只谈模型结构与损失函数（岗位是数据/平台，不是研究）。
- 无延迟/成本分解，无降级路径。
- 把订单下跌归因为"实验噪声"而不做检验。
- 特征一致性只说"统一从一份表取"（没有时点、没有对拍）。
- 实验按访客随机、无 SRM 检查、无护栏指标。
- 对新供给只做"加权提权"这种无退出机制的做法。

### 题面草稿 B（`code`，`judgeKind=mysql`）
> **搜索质量的口径题（Airbnb 风格：一个数字三种答案）**
> 给定 `search_session(session_id, user_id, ts, query_geo, n_results)`、`search_click(session_id, listing_id, ts, position)`、`booking(session_id, listing_id, ts, gmv)`。
> 要求：
> 1) 计算"搜索→预订转化率"：口径 A（会话内任意位置点击后预订）与口径 B（最后一次点击即被预订，即 KDD'18 风格的 last-viewed booking），两列输出，明确分母定义；
> 2) "无结果率"：分别按会话数与按用户数统计，且必须排除"用户被限流导致 0 结果"的记录（题面给出 `n_results=0 AND is_ratified=1` 的语义）；
> 3) 位置偏差检测：给出"位置 1 的点击占比 / 位置 1 的曝光占比"随 query 类别的分布（要求处理未点击会话的分母）；
> 4) 找出"重复搜索同一查询 30 分钟内 >=3 次"的会话簇（gaps & islands，题面给时间阈值）并统计其后续转化率——业务含义写在注释（rubric 版会看）。
> 用例：跨会话预订、点击未预订、0 结果但被限流、位置并列、簇边界（正好 30 分钟）。

区分度：分母与去重口径是否写清、能否正确实现"最后一次点击即预订"。
