## 1. 核心机制（必须能画出来，并且能说清"谁在哪一层负责"）

### 1.1 一笔下单的链路（把"事务"拆成四个不同语义位置）
```
接入层：鉴权 + 入口限流（Sentinel 入口 QPS / 系统自适应保护）
  → 交易服务：幂等键校验（请求 ID / 订单号唯一约束）
  → 状态机推进 + 本地事务（同库同事务写：订单表 + 幂等表 + outbox/半消息）
  → 库存：热点行 UPDATE（单行串行 → 内核攒批/流水线；或先缓存预扣再落库）
  → 跨服务一致性：事务消息（半消息 + 二次确认 + 回查）/ Seata 全局事务（AT 全局锁、TCC 二阶段）
  → 异步侧：MQ 堆积削峰 → 下游（营销、积分、购物车、履约）按自身能力消费 + 幂等去重
  → 兜底：定时消息做超时关单；对账任务修差异
横切：服务治理（健康检查/无损上下线/预热/泳道灰度）、限流熔断降级、可观测
```
- 核心判断：**"强一致"和"最终一致"不是同一个问题的答案**。Seata/PolarDB-X 解决"一个业务写多个库不能出现中间态"；事务消息解决"本地事务成功但下游没收到"；对账兜住前两者漏掉的数据。三层各自要能举一个失效场景【推】。
- 官方对事务消息的定位可直接引用："提供类似 XA 或 Open XA 的分布式事务功能……达到分布式事务的**最终一致**"；价值不是"更强一致"，而是"**不会因为某一个关联应用的不可用导致整体回滚，从而最大限度保证核心系统的可用性**"（官方例子就是淘宝购物车下单：交易系统是最核心系统，要保证下单成功；购物车只订阅订单消息做处理）【源 S4】。这句话是"你为什么不用 2PC"的标准答案骨架【推】。

### 1.2 库存扣减：热点行是"物理串行"，分库分表救不了它
PolarDB 文档对问题的表述可以直接引：更新顺序是 `LOCK -> UPDATE -> UNLOCK`，同一行大量修改造成锁争抢与锁等待，"请求量增加会导致 TPS 下降，延迟飙升"；并且明写"**对于单一热点行的更新请求实际上是串行执行的，传统的分库分表策略在性能提升方面并不会有太大帮助**"【源 S8】。这是"背过分库分表"与"真扛过秒杀"的分水岭。
- 内核侧三条优化（逐条对得上机制）：① **串行变流水线**——内核自动识别带 `autocommit` 或 `COMMIT_ON_SUCCESS` 标记的更新，在一定时间间隔内按主键/唯一键 Hash 分桶、按到达先后分组分批处理与提交，两个分组交替收集/提交、并行执行；② **消除申请行锁的等待**——组内第一个更新是 Leader（读目标行并加锁），后续 Follower 发现 Leader 持锁时"无需等待，直接获得行锁"；③ **减少 B-tree 索引遍历**——只有 Leader 遍历索引，之后把更新后的数据行缓存在内存 Row Cache，Follower 直接取行【源 S8】。
- 参数与代价：`hotspot` 是总开关（默认 OFF，控制台参数带 `loose_` 前缀）；`hotspot_update_max_wait_time` 默认 **100us**（Leader 等待 Follower 加入分组的时间）；`hotspot_lock_type` 默认 OFF；前提是**已开启 Binlog**，且 MySQL 5.7 默认开启 `rds_ic_reduce_hint_enable`、需先改为 OFF【源 S8】。官方性能锚点是"单热点行 + 8 核 CPU 场景下，库存热点性能在高并发时提升近 50 倍"，并给了并发 1→1024 的 QPS 对照表（**并发为 1 时开启反而更慢：1114.79 vs 1365.31**）【源 S8】——"低并发下是负收益"比"提升 50 倍"值钱得多。
- 失效边界（高频追问）：分区表、有触发器的表、已使用 Statement Queue 的行、全局 Binlog 开启但会话级 Binlog 关闭时，热点行优化**不会被使用**；开启后"**仅依赖 `ON UPDATE CURRENT_TIMESTAMP` 属性自动更新的列会失效**"，需显式 `SET column_name = CURRENT_TIMESTAMP(n)`【源 S8】。
- 语义件（Inventory Hint）：`COMMIT_ON_SUCCESS`（本条成功即提交，连同之前未提交的语句一起提交）、`ROLLBACK_ON_FAIL`、`TARGET_AFFECT_ROW number`（实际影响行数不等于设定值则语句失败）；支持 SELECT/UPDATE/INSERT/DELETE；PolarDB MySQL 8.0 下 `COMMIT_ON_SUCCESS`/`ROLLBACK_ON_FAIL` **不能运行在 autocommit 模式**，直接报 `ERROR 7531 (HY000): Inventory transactinal hints didn't allowed in autocommit mode`【源 S9】。三件套 = 把"提交/回滚决策"下推到语句级，从而让"扣减 + 提交"只花一次往返【推】。
- 排队件（Statement Queue）：`ccl_queue_filed("id")` 需通过 `DBMS_OUTLN.add_optimizer_outline` 注入 Optimizer Hint，且文档明确要求 **`COMMIT_ON_SUCCESS` 必须在 `ccl_queue_filed` 前面**，顺序反了会报错；官方示例正是 `UPDATE t2 SET kucun = kucun - 1 WHERE id = 100 AND kucun > 0`【源 S10】——"hint 顺序即语义"是使用过的痕迹。
- 分布式版（PolarDB-X）约束更硬：热点更新（INVENTORY HINT）**只支持单分片事务，不支持跨数据库场景**；WHERE 必须是**主键或唯一键的等值条件**，且**不支持带有全局索引的表**（可含本地索引）；前置需 `SET GLOBAL HOTSPOT=ON`、`HOTSPOT_LOCK_TYPE=ON`、关闭共享 ReadView（`SHARE_READ_VIEW=FALSE`，文档同时警告"全局关闭可能会导致一部分查询变慢"）、事务类型必须是 XA 且 `ENABLE_XA_TSO=FALSE`；并提醒 `SET GLOBAL` 对当前会话不生效、需重开会话【源 S11】。→ 追问"为什么要求关掉 TSO"：组提交依赖本地串行 + 语句级提交，跨节点全局授时会把等待重新变成分布式等待【推】。

### 1.3 幂等：官方口径就是"业务必须自己做"
- RocketMQ 在《消费者负载均衡》里直接给结论：**消费者上下线、服务端扩缩容都会触发短暂的重新负载均衡，此时可能存在短暂的负载不一致、出现少量消息重复，因此"需要在下游消费逻辑中做好消息幂等去重处理"**【源 S3】。也就是说：**投递语义不是 exactly-once，重复是设计内事件而不是故障**。
- 但重复来源分两类，窗口不同：① 队列粒度负载均衡"每个队列仅支持被一个消费者消费"、消息粒度"服务端会将该消息加锁，保证对其他消费者不可见，直到该消息消费成功或消费超时"——这两类**不会**被重复消费【源 S3】；② 发送侧超时重试——文档明说"客户端因请求超时触发消息发送重试流程时无法感知服务端处理结果，**可能会产生消息重复问题，业务逻辑需要自行处理消息重复问题**"【源 S2】。
- 消费端的两种"错误写法"被点名：消息未处理完就返回成功（服务端无法感知失败 → 不重试）；在监听器内把消息分发到自定义线程并提前返回结果（同上，且**顺序消费也无法保证顺序**）。另有一条极易被忽略的机制：PushConsumer 判定消费超时后 SDK 会强制提交失败结果，"但是当前消费线程可能仍然无法响应中断，还会继续处理消息"——这正是"超时 + 重试"叠加出重复的根因【源 S12】。
- 锁这一侧（Tair 文档，"结合阿里巴巴集团在使用 Tair（企业版）和分布式锁方面的业务经验"）：Redis 主备同步是**异步**的，HA 切换时"缓冲区的数据可能无法同步到新 master，导致数据不一致；如果丢失的数据跟分布式锁有关，则会导致锁的机制出现问题"；自锁自解与续租需要 Lua（并指出 `CAS` 命令**不检查新旧 value 是否相同**）；红锁本质是概率解（丢锁概率变 (k%)^N），代价是"难以在集群版或标准版（主备架构）实例中实现""占用资源过多"；`WAIT` 会阻塞客户端；Tair 侧用 CAS/CAD 降低开发成本，内存型实例"能提供三倍于原生 Redis 的性能"，且支持配置主备**半同步**（写入并同步到备节点后才返回；备节点故障/网络异常时**降级为异步**以保证可用）【源 S33】。→ 面试标准问："你的锁在 HA 切换后还成立吗？不成立的后果是超卖还是重复发货？"【推】

### 1.4 削峰与堆积：位点、存储时长、冷读三件事互相牵制
- 堆积有定义，不是"队列长度"：`MaxOffset − ConsumerOffset` 即该队列堆积量；有效位点必须 `ConsumerOffset ≥ MinOffset`，若历史位点已过期被删除，"服务端会将消费位点强制纠正到合法的消息位点"（→ 那段消息**已经没了**）【源 S6】。位点由**服务端**存储、"和任何消费者无关"，所以支持跨消费者的进度恢复【源 S6】。
- 削峰的物理边界：RocketMQ **以"存储时长"为存储依据**（在时长内的消息无论是否消费都保留，超过即清理），且**按存储节点粒度**管理，不按 topic/queue；官方理由："存储层本质还是共享存储介质……整个集群仍然存在容量风险，可能会导致存储时长 SLA 被打破"，并建议"将不同存储时长的消息通过不同集群进行分离治理"【源 S7】。→ 结论：堆积不是免费的；超过存储时长就等于永久丢消息，此时重置位点也救不回来【推】。
- 服务端会**反向流控**（最容易被忽略的一条）：触发条件为"存储压力大"（例如业务上新需要回溯到历史位点，队列存储压力瞬间飙升）与"服务端请求任务排队溢出"（消费能力不足导致堆积超一定数量后触发流控，减少下游压力）；客户端收到 `reply-code：530 / reply-text：TOO_MANY_REQUESTS` 后按**指数退避**重试发送。文档给的建议是"用可观测性监控系统水位容量、保证底层资源充足"，突发流控时"建议业务方将请求调用临时替换到其他系统进行应急处理"【源 S2】。→ "消息削峰"的另一面：**MQ 也在削上游**【推】。
- 回溯与冷读：重置消费位点的三个官方场景（初始位点不符预期、快速清理可丢弃的堆积、业务回溯纠正处理）；能力上"只能重置对消费者可见的消息，**不能重置定时中、重试等待中的消息**"；警告"重置后的历史消息大多属于存储冷数据，可能造成系统压力上升（冷读现象），建议严格控制重置消费位点接口的调用权限"【源 S6】。另一条版本兼容坑（升级必读）：**5.x 明确定义消费位点初始值为"消费者获取消息时刻队列中的最大位点"，而 4.x/3.x 的初始值"受当前队列消息状态影响"**，从历史版本升级到 5.x 需"自行对消费者首次启动时的情况做兼容性判断"【源 S6】。
- 消费重试是"削峰的副作用"：普通消息（非顺序）重试间隔为**阶梯时间**——第 1 次 10 秒、第 2 次 30 秒、第 3 次 1 分钟、第 4 次 2 分钟、第 5 次 3 分钟……第 13 次 20 分钟、第 14 次 30 分钟、第 15 次 1 小时、第 16 次 2 小时，且"**若重试次数超过 16 次，后面每次重试间隔都为 2 小时**"；**最大重试次数本身由"消费者分组创建时的元数据"控制、支持自定义**（别把它记成"固定 16 次"，16 只是阶梯表的顶端）；"如果最大重试次数为 3 次，则该消息最多可被投递 4 次，1 次为原始消息，3 次为重试投递次数"；重试由五状态驱动（Ready / Inflight / WaitingRetry / Commit / DLQ），达到最大重试次数仍失败则"消息不会再重试，会被投递至死信队列"，DLQ 被定义为"消费逻辑的最终兜底机制，可以通过消费死信队列的消息进行业务恢复"；顺序消息的重试间隔为固定时间（取值见参数限制）；SimpleConsumer 的重试间隔是**预分配**的 `InvisibleDuration`（即消息的最大处理时长），"若消息消费失败触发重试，不需要设置下一次重试的时间间隔，直接复用不可见时间参数的取值"，且"**消息重试间隔 = 不可见时间 − 消息实际处理时长**"（例：不可见 30ms、处理 10ms 返回失败 → 间隔 20ms；直到 30ms 仍未处理完成且未返回结果则消息超时、**立即重试、间隔为 0ms**），修改不可见时间需满足"消息处理未超时 + 消息处理未提交消费状态"，改后立即生效并从调用 API 时刻重新计时；两条使用建议是"**合理重试，避免因限流等诉求触发消费重试**"（错误示例：消费速度过高触发限流就返回消费失败等下次重消费；正确示例：延迟获取消息稍后再消费）与"**合理控制重试次数，避免无限重试**：建议通过减少重试次数 + 延长重试间隔来降低系统压力"；另有时间约束"两次消费间的间隔时间实际由消费耗时及重试间隔控制，**消费耗时的最大上限受服务端系统参数控制，一般不应该超过上限时间**"【源 S13】。
- 定时消息（超时关单的标准件）：定时值是**毫秒级 Unix 时间戳**（不是时长）；必须落在定时时长范围内，"超过范围则定时不生效，服务端会立即投递"；必须设置在未来，否则同样立即投递；**定时时长最大值默认为 24 小时，不支持自定义修改**；官方场景直接写"订单下单后暂未支付……需要等待一段时间后才能关闭订单"，并把优势写成"精度高、开发门槛低""高性能可扩展（对比传统数据库扫描）"【源 S15】。→ 追问"15 分钟关单怎么做、3 天呢"（24 小时上限 → 分段续投或外部调度）【推】。

### 1.5 限流、熔断、降级：三件事的粒度不同（Sentinel 视角，逐条可对上）
- 限流有两个 grade：**并发线程数（0）**与 **QPS（1）**。线程数限流的目的是"保护业务线程数不被耗尽"，并明确"Sentinel 线程数限流不负责创建和管理线程池，而是简单统计当前请求上下文的线程个数，超出阈值新请求立即拒绝"；文档对比了线程池/信号量隔离"能控制线程数量，但无法控制请求排队时间"【源 S16】。
- 通过策略三种（`controlBehavior`）：直接拒绝（默认，"适用于对系统处理能力确切已知的情况，比如压测确定了准确水位"）、**冷启动 Warm-Up**（长期低水位时"直接把系统拉升到高水位可能瞬间把系统压垮"，让流量缓慢增加）、**匀速排队 RateLimiter = 漏桶**（"严格控制请求通过的间隔时间"，"主要用于处理间隔性突发的流量，**例如消息队列**"）【源 S16】。→ 一句话取舍：保命用直接拒绝，保请求不丢用漏桶，冷系统必须 Warm-Up【推】。
- 还能按**调用方**和**调用链入口**限流：`limitApp` ∈ `default / {some_origin_name} / other`，同资源多规则的生效顺序 **`{some_origin_name} > other > default`**；调用树根是虚拟节点 `machine-root`，其子节点才是入口；统计来自 `NodeSelectorSlot` + `ClusterNodeBuilderSlot`，限流在 `FlowSlot` 执行，被限流表现为抛 `FlowException`（`BlockException` 子类）【源 S16】。
- **热点参数限流**：官方例子就是"商品 ID 为参数，统计一段时间内最常购买的商品 ID 并进行限制""用户 ID 为参数，针对一段时间内频繁访问的用户 ID 进行限制"；实现是"利用 **LRU 策略统计最近最常访问的热点参数，结合令牌桶算法**进行参数级别的流控"，且"仅对包含热点参数的资源调用生效"，需独立引入 `sentinel-parameter-flow-control`【源 S20】。→ 大促爆款单 SKU 的限流就是这一条【推】。
- **集群限流**：两种身份（Token Client / Token Server），1.4.0 引入，client/server 默认实现基于 Netty，server 侧通过扩展接口对接 `TokenService`；规则里 `clusterMode` + `ClusterFlowConfig`，且需要"**由集群限流管控端分配的全局唯一规则 ID**"；最关键的失效语义：**"若用户未引入集群限流 client 相关依赖，或者 client 未开启/连接失败/通信失败，则对于开启了集群模式的规则：普通集群限流会退化到 local 模式的限流，即在本地按照单机阈值执行限流检查"**（并提供"连接失败或通信失败时是否退化到本地"的配置项）【源 S19】。→ 追问"限流中心挂了是放行还是拒绝"，官方答案是**按单机阈值拒**【源 S19】。
- 熔断三种策略都自带恢复判据：**慢调用比例**（配允许的最大 RT，`statIntervalMs` 内请求数 > 最小请求数且慢调用比例 > 阈值 → 熔断时长内自动熔断；熔断时长后进入 **HALF-OPEN 探测恢复**，接下来一个请求 RT 小于慢调用 RT 则结束熔断，否则再次熔断）、**异常比例**（阈值域 [0.0, 1.0]）、**异常数**；并明确"**异常降级仅针对业务异常，对 Sentinel 限流降级本身的异常（BlockException）不生效**"，需用 `Tracer.trace(ex)` 记录（`if (!BlockException.isBlockException(t))` 的经典写法），而 Sentinel Dubbo Adapter / Web Servlet Filter / `@SentinelResource` 会自动统计【源 S17】。→ 这就是"熔断了但大盘不红"的答案之一：**你自己抛的限流异常不计入业务异常**【源 S17】。
- 系统自适应保护不是"load 超阈值就禁流"：官方先点名旧做法的真实故障——"下游应用不可靠导致 RT 很高、load 冲高；下游恢复后 RT 降下来，但此时 load 仍高，通过率恢复不了"，并给出结论"无论怎么调参数、调比例，都是**按照果来调节因**"；Sentinel 的做法是"**用 load1 作为启动控制流量的值，而允许通过的流量由处理请求的能力（响应时间 + 当前正在处理的请求速率）决定**"，推导式是 `T ≈ QPS × Avg(RT)`（水管模型），系统容量由 **maxQps × minRt** 计算，Load 阈值"设定参考值一般是 **CPU cores × 2.5**"；系统规则是**应用整体维度、仅对入口流量（EntryType.IN）生效**；除 Load 外还有 CPU usage（1.5.0+，0.0–1.0）、RT、线程数、入口 QPS 四类【源 S18】。

### 1.6 服务治理：健康检查 + 上下线 + 灰度（阿里栈的三块拼图）
- 注册中心侧（Nacos）："提供对服务的实时的健康检查，阻止向不健康的主机或服务实例发送请求"，支持**传输层（PING 或 TCP）与应用层（HTTP、MySQL、用户自定义）**两级检查，并提供 **agent 上报模式与服务端主动检测两种模式**（针对 VPC、边缘网络等复杂拓扑），另有统一健康检查仪表盘与权重路由；"动态 DNS 服务……帮助您消除耦合到厂商私有服务发现 API 上的风险"【源 S26】。→ 面试点：健康检查放**哪一层**决定它能发现什么（进程活着 ≠ 能处理请求）【推】。
- RPC 容错语义与幂等直接耦合（Dubbo 集群容错）：**Failover**（"失败自动切换，当出现失败，重试其它服务器。通常用于读操作，但重试会带来更长延迟"，`retries="2"` 设重试次数且**不含第一次**）、**Failfast**（"快速失败，只发起一次调用，失败立即报错。通常用于非幂等性的写操作，比如新增记录"）、**Failsafe**（忽略异常，用于写审计日志）、**Failback**（后台记录失败定时重发，用于消息通知）、**Forking**（并行调多个提供者一个成功即返回，"用于实时性要求较高的读操作，但需要浪费更多服务资源"，用 `forks` 设并行数）、**Broadcast**（逐个调用所有提供者，"任意一台报错则报错"；`broadcast.fail.percent`（2.7.10+）如 20% 节点失败就不再调用其他节点，但"**并不改变结果**"）、**Available**（只调当前可用实例，"通常用于不需要负载均衡的场景"）、**Mergeable**（按 group 聚合结果）、**ZoneAware**（多注册中心选址，`preferred="true"` 优先）【源 S22】。→ 一句话："重试策略的默认值配错，就是重复发货/超卖的第一现场"【推】。
- 负载均衡（Dubbo）：**缺省为 random 随机**；加权随机按权重设概率；加权轮询"借鉴 Nginx 的平滑加权轮询算法"，解决"某节点权重过大时某段时间调用过于集中"（原始轮询 A A A B B C → 平滑后分散）；**LeastActive（最少活跃调用优先 + 加权随机）"背后是能者多劳的思想"**，活跃数定义为"针对特定提供者：请求发送数 − 响应返回数"，即任务堆积量；**ShortestResponse** 依据"最近一个滑动窗口"中的响应时间【源 S23】。→ 追问"最少活跃 vs 最短响应"：前者看**在途堆积**（对慢启动/预热敏感），后者看**历史 RT**（对偶发抖动敏感）【推】。
- 发布期的流量损失（MSE）：官方先否掉"选在流量小的时间发布"（"不可控因素引起的运维成本也很高"），再给做法——**下线阶段引入自适应等待和主动通知机制，确保所有待处理请求完成后再执行下线**；**上线阶段通过就绪检查，并把微服务生命周期管理与发布的各个阶段精准对齐**【源 S24】。配套的**服务预热**：控制台"无损上线"开关里**预热时长默认 120 秒**，"开启预热功能的应用重启后的流量会随时间缓慢增加"，用途是"应用启动过程中需要预建连接池和缓存等资源的慢启动场景"【源 S24】。→ 量化直觉：预热窗口短于 JIT/连接池到达稳态的时间等于没做【推】。
- 全链路灰度 = **标签路由 + 泳道**：灰度节点需打 `alicloud.service.tag=${tag}`（容器环境放 `spec.template.metadata.labels`，ECS 环境放 JVM 参数 `-Dalicloud.service.tag=`）；泳道配置含"泳道标签 + 泳道应用列表 + 请求内容匹配条件"（示例覆盖 header 精确等于、32 位字母数字正则、header 百分比 10）；**最关键的兜底语义**："满足规则的流量会**优先**流向标记有当前泳道对应标签的应用版本，**如果没有对应标签的应用版本则流向未打标的应用版本**"（回落基线而不是丢请求）；文档同时提醒"全链路灰度整合了标签路由功能，因此不推荐已经加入全链路流量控制的应用再配置金丝雀发布和标签路由"【源 S25】。→ 追问：MQ 消费、定时任务这类**没有 header 的入口**如何带标签？本文件按【推】处理（无官方描述，见 §7）。

### 1.7 分库分表与"一致性从哪来"
- 拆分键选择是官方口径："数据表拆分的首要原则是**尽可能找到数据所归属的业务逻辑实体**，并确定大部分（或核心的）SQL 操作或者具备一定并发的 SQL 都围绕这个实体进行，然后可使用该实体对应的字段作为拆分键"；机制上"将拆分键值通过拆分函数计算得到结果，据此把数据分拆到私有定制 RDS 实例上"【源 S27】。→ 反面信号：按"创建时间"拆订单表，会让"查某买家的订单"变成全库扫【推】。
- 唯一性坑（官方原话）："**分库分表中，分表内保证主键的唯一性，但是主键在分库分表中不保证唯一性**，如有需要可使用全局唯一索引"【源 S29】。→ 全局唯一 **ID**（序列：雪花/号段/DB sequence）与全局唯一 **约束**（索引）是两件事【推】。
- 二级索引的代价："GSI 支持按需增加拆分维度、提供全局唯一约束。**每个 GSI 对应一张索引表，使用 XA 多写保证主表和索引表之间数据强一致**"；语法上索引表有自己的分库分表子句，`COVERING` 覆盖列"默认包含主键和主表的分库分表键"【源 S28】【源 S29】。→ 每次写主表都要同步写索引表 = 多一次分布式写 + XA，这就是"GSI 拖慢写"的官方依据，也与热点行优化互斥（PolarDB-X 热点更新明写不支持带全局索引的表）【源 S8/S11】。
- 分布式事务底座（PolarDB-X）：中心授时节点 **TSO** 生成"全局单调递增的时间戳"，结合 **MVCC** 提供一致性快照读（CN 提交时从 TSO 取时间戳，随数据一同提交到 DN 多版本引擎）；元数据服务 **GMS** "基于 Paxos 共识协议提供一个具备三节点高可用性的服务"，CN 通过 RPC 与之通讯获取全局时钟；写入涉及多分区时 CN 用 **2PC** 提交，"即便在事务提交过程中发生节点宕机等问题，基于 2PC 的事务恢复机制也能确保事务原子性"；对账型查询 `SELECT SUM(balance) FROM account` 会先取全局时钟作为读取版本、**逐行做 MVCC 可见性判断**，从而"已提交但版本号不满足可见性的分支全部不可见"【源 S30】。
- 同一篇里的读写分离、CDC 与 PITR（三条都可核查）：主实例由"基于 Paxos 多数派的 Leader/Follower 角色"组成、**只读实例由 Learner 角色**组成；DN leader 主副本保存事务信息之外，"**也会将数据的事务多版本信息同步到 learner 副本中**，可以保证只读实例上的多个分区数据读的一致性"；官方例子里"写入版本 100 的数据，下次查询带着全局时钟返回的版本 101 路由到 learner 时，即使有复制延迟，**PolarDB-X 也可以阻塞读来满足读的一致性**"；下游 CDC 通过日志组件"收集、重组、排序、落盘"多个 DN 的日志流，"提供满足分布式事务一致性语义的二进制日志"（事务不乱序、原子性、DDL 同步）且兼容 MySQL binlog 协议；PITR 侧"任意时间点的数据恢复都可以快速将时间戳转化为分布式的全局时钟，在备份恢复中按数据的版本可见性进行处理"【源 S30】。
- RO 读一致性的产品化描述（PolarDB PostgreSQL 版《全局一致性》，非常适合出题）：一写多读架构中"**RO 节点默认提供会话一致性读取**"，物理复制与共享存储"可以有效降低 RO 节点的复制延迟，但**不能保证**发往 RO 节点的只读请求读取到 RW 节点上最新写入的数据"；文档画出的正是交易链路的经典事故：**服务 A 写入成功 → 通过消息队列通知服务 B → 服务 B 直接读 RO，很可能读不到最新值**，于是业务只能把读请求转发到 RW，"RO 节点资源也因此被闲置"；开启全局一致性后，"RW 节点上每个读写事务提交时都会赋予一个 **CSN（Commit Sequence Number）**……以替代原生 PostgreSQL 的活跃事务列表"，CSN 记录进 WAL，"RO 节点通过回放 WAL 构建出完整的事务状态"，从而提供集群维度的强一致读；金融与游戏行业被列为典型需求方【源 S31】。
- 同层的另一条路线（OceanBase 系统架构）：表按 Hash/Range/List（支持二级分区）水平拆为分区，"每行数据属于且只属于一个分区"，每个物理分区有一个存储层对象叫 **Tablet**；修改 Tablet 记录 Redo 到其**日志流（Log Stream）**，"每个日志流用于服务其所在节点上的多个 Tablet"；为防单点，"每个日志流及其所属的 Tablet 有多个副本，一般来说多个副本分散在多个不同的可用区里"，其中"有且仅有一个副本接受修改操作"（Leader），主从副本之间"**通过基于 Multi-Paxos 的分布式共识协议**实现副本间数据一致性"，主副本节点故障时从副本被选举为新主；节点上运行对等的 observer 进程；租户 / 资源单元 Unit / 资源池做隔离；应用侧通过 **ODP（OBProxy，无状态，配合 SLB）** 屏蔽分区与副本分布细节；另有基于通用对象存储的**共享存储（SS）模式**（存算分离：主副本上传全量日志与基线到对象存储、副本间共享基线、各副本"自动识别日志/数据热度"仅在本地缓存热点、**每个副本独立转储且转储数据不共享**）【源 S32】。→ 追问"分区/副本/Leader 切换与应用有什么关系"：Leader 切换是常态，**客户端必须容忍重试与短暂不可用**【推】。

## 2. 会被追问什么（阿里风格：从"你怎么用"问到"你怎么证明它对"）

1. "为什么库存不能只靠缓存扣？"（Redis 主备异步复制、HA 切换可能丢数据丢锁【S33】；最终仍需 DB 侧带条件的原子扣减 + 对账兜底【推】）
2. "你的扣减 SQL 长什么样？如何区分'没抢到'和'库存不足'？"（`WHERE id=? AND kucun>0` 与 `TARGET_AFFECT_ROW` 的语义差；affected rows=0 的两种含义要能分开【S8/S9】＋【推】）
3. "热点行优化为什么低并发反而更慢？"（官方对照表：并发 1 时 1114.79 vs 1365.31；攒批要等 `hotspot_update_max_wait_time`=100us）【S8】
4. "分库分表之后为什么单行热点还要单独治？"（官方原话："分库分表策略在性能提升方面并不会有太大帮助"）【S8】
5. "半消息一直没收到二次确认会怎样？谁来判断？"（服务端定时回查；生产者按本地事务最终状态再次确认；回查间隔/次数由服务端控制）【S1/S4】
6. "回查里你应该查什么？"（只能查**本地事务状态表/订单状态**，不能"再执行一次本地事务"；答"重跑"直接判负【推】）
7. "消息重复是 bug 还是设计？"（重平衡 + 发送超时重试 → 官方要求下游做幂等去重）【S3/S2】
8. "PushConsumer 里为什么禁止异步化处理？"（监听器提前返回 → 服务端无法感知失败、不重试；顺序消费同时失效）【S12】
9. "你的堆积上限配多少？超了会怎样？"（排队溢出触发服务端流控 `530 TOO_MANY_REQUESTS`，客户端指数退避）【S2】
10. "回溯一周的消息，先看什么？"（存储时长是否覆盖（按存储节点粒度、不区分是否消费）、冷读压升、不能重置定时中/重试等待中的消息、位点是否已被强制纠正）【S6/S7】
11. "订单 30 分钟未支付关单怎么做？3 天后自动取消呢？"（毫秒时间戳语义、默认最长 24 小时不可改 → 续投或外部调度）【S15】
12. "熔断了但大盘不红，为什么？"（BlockException 不计入业务异常；缺"熔断/降级触发率"这条独立曲线）【S17】
13. "集群限流的 Token Server 挂了怎么办？"（退化到本地按单机阈值限流；可配置是否退化；容量陷阱）【S19】
14. "为什么不直接按 load 限流？"（BBR 式：load1 只做启动控制，通过量由 RT × 并发/处理能力决定，否则"按果调因"、恢复慢）【S18】
15. "重试几次、重试谁？"（读用 Failover、非幂等写用 Failfast；Forking 用资源换尾延迟；Broadcast 任一台失败即失败且 `fail.percent` 不改变结果）【S22】
16. "新机器一上线就被打挂，你怀疑什么？"（预热窗口与连接池/缓存冷启动、就绪检查、默认随机分配让新实例瞬间被均摊）【S24/S23】
17. "灰度泳道里没有灰度版本的下游节点怎么办？"（官方语义：流向未打标的基线版本；同时要说"标签未透传/丢失"的排查路径）【S25】
18. "GSI 让写慢了多少？为什么？"（每个 GSI 是一张索引表 + XA 多写强一致；一次业务写放大为多分片写）【S28】
19. "写后马上读读到旧值，是应用问题还是副本问题？"（会话一致性 vs 全局一致性、CSN/RO 阻塞读、复制延迟指标）【S31/S30】
20. "对账发现 3 笔不一致，怎么归因？"（分层：本地事务/半消息状态、消费幂等键、热点行回滚、位点被纠正到 MinOffset（消息已删）、Leader 切换 + 重试）＋【推】

## 3. 常见错误答案（背题型信号）

| 错误 | 暴露点 |
|---|---|
| "库存扣减加个 Redis 分布式锁就行" | 不知热点行是**内核级串行**问题、不知 Redis 主备异步复制会丢锁【S8/S33】 |
| "分布式事务一律上 Seata AT" | 说不出 AT 的**默认全局隔离级别是读未提交**、"拿不到全局锁不能提交本地事务"、回滚会被等待中的全局锁卡住并一直重试【S5】 |
| "事务消息 = 消息不丢" | 混不清"半消息 + 回查"与"消费重试/幂等去重"是两段不同责任【S1/S4】 |

## 4. 考点清单（14 条）

1. **分布式事务模式选型与代价**（`alibaba-distributed-transaction-mode`）
   要点：Seata 定位"开源的分布式事务解决方案，提供 AT、TCC、SAGA 和 XA 事务模式"【源 S34】；AT 前提是"基于支持本地 ACID 事务的关系型数据库 + Java 通过 JDBC 访问"，本质是"两阶段提交协议的演变"：一阶段把**业务数据与回滚日志（UNDO_LOG）在同一本地事务中提交**并释放本地锁，二阶段"提交异步化，回滚通过一阶段的回滚日志进行反向补偿"【源 S5】；TCC 要求每个分支事务具备"一阶段 prepare 行为 + 二阶段 commit/rollback 行为"，即把资源预留/取消预留写进业务接口【源 S35】；XA 的官方批评可直接引：基于 XA 协议"可以满足业务处理结果的正确性，但最大的缺点是多分支环境下资源锁定范围大，并发度低，随着下游分支的增加，系统性能会越来越差"；而事务消息的思路正是"将订单系统变更作为本地事务，剩下的系统变更作为普通消息的下游来执行，事务分支简化成普通消息 + 订单表事务，充分利用消息异步化的能力缩短链路，提高并发度"【源 S1】。选型账：AT 零侵入但受全局锁限制（热点行场景退化）；TCC 性能与语义最好但补偿成本落在业务；事务消息只保最终一致、换来解耦与可用性【推】。
   出题：rubric（"下单 + 扣库存 + 扣券 + 加积分"四步各自选模式，写明"哪些可补偿、哪些必须回滚、谁的失败不能拖垮主流程"）；code（模拟两个全局事务更新同一行：断言"拿不到全局锁不能提交本地事务""等锁超时则回滚本地事务释放本地锁"）。
   judgeKind：`llm-rubric` ＋ `java-junit`。
   锚点：【源 S34】【源 S5】【源 S35】【源 S1】＋【推（成本账）】。
2. **AT 模式的写隔离、全局锁与"默认读未提交"**（`alibaba-seata-at-locking`）
   要点：写隔离三条硬规定——"本地事务提交前需先拿到全局锁""拿不到全局锁不能提交本地事务""拿全局锁的尝试被限制在一定范围内，超出则放弃并回滚本地事务释放本地锁"【源 S5】；回滚链路的死锁味道要能讲：tx1 二阶段全局回滚需重新拿本地锁做反向补偿，若 tx2 仍在等全局锁且持有本地锁，"tx1 的分支回滚会失败、一直重试"，直到 tx2 全局锁等锁超时并回滚本地事务【源 S5】；读隔离默认值必须背准——"在数据库本地隔离级别读已提交或以上的基础上，Seata（AT 模式）的**默认全局隔离级别是读未提交**"，要全局 RC 只能靠 `SELECT ... FOR UPDATE` 的代理（申请全局锁、被持有则释放本地锁并重试），且"出于总体性能考虑，Seata 并没有对所有 SELECT 语句进行代理，仅针对 FOR UPDATE 的 SELECT 语句"【源 S5】。
   出题：code（简化 TC：本地事务 + 全局锁 + 等锁超时的状态机，断言低峰重试与超时回滚两条路径 + 回滚被阻塞时的重试行为）；rubric（AT 与热点行优化同用一行时的吞吐与死锁风险）。
   judgeKind：`java-junit` ＋ `llm-rubric`。
   锚点：【源 S5】＋【推（全局锁把行锁等待搬到 TC 层）】。
3. **事务消息与回查：本地事务与投递的耦合点**（`alibaba-transactional-message`）
   要点：流程要能默写——① 生产者把消息发到服务端；② 服务端持久化成功回 Ack，此时消息"被标记为**暂不能投递**"，即半事务消息；③ 生产者执行本地事务；④ 按本地事务结果提交二次确认：Commit → 服务端标记为可投递并投递给消费者；Rollback → 回滚、不投递；⑤ 若未收到二次确认或结果为 Unknown，"**在经过固定时间后，服务端将对消息生产者即生产者集群中任一生产者实例发起消息回查**"（回查的间隔时间与最大回查次数见"参数限制"），生产者收到回查后需"检查对应消息的本地事务执行的最终结果"；另有三条实战建议：一般要为事务消息设置"一个本地事务关联的唯一 ID，用来做本地事务回查的校验"；"**回查时对于正在进行中的事务不要返回 Rollback 或 Commit 结果，应继续保持 Unknown 的状态**"（成因是"事务执行较慢，消息回查太快"，解法是"将第一次事务回查时间设置较大一些，但可能导致依赖回查的事务提交延迟较大"）；以及"生产者应该尽量避免本地事务返回未知结果，**大量的事务检查会导致系统性能受损，容易导致事务处理延迟**"【源 S1】。云侧口径补充：回查的成因是"网络闪断、生产者应用重启等原因导致二次确认丢失"，服务端通过**扫描**发现长期处于半事务状态的消息才询问；定位是"达到分布式事务的**最终一致**"；价值是"把大事务拆成小事务，不因某个关联应用不可用整体回滚，最大限度保证核心系统可用性"，极端情况下"只需对当前应用进行补偿或数据订正，而无需对整体业务回滚"（淘宝购物车 vs 交易系统）【源 S4】。
   出题：code（`HalfMessageStateMachine`：提交/回滚/回查三路径 + "回查只能查本地事务状态表，不得重复执行本地事务"的断言）；code（`mysql`：本地事务表 + outbox，产出"本地成功但消息未投出 / 本地回滚但消息已投出"两类脏数据的对账 SQL）。
   judgeKind：`java-junit` ＋ `mysql`。
   锚点：【源 S1】【源 S4】＋【推（outbox 与对账口径、幂等键设计）】。
4. **库存扣减与热点行优化**（`alibaba-inventory-hotrow`）
   要点：`LOCK → UPDATE → UNLOCK` 的串行本质 + "分库分表帮不上"；三条内核优化（流水线分组、Leader/Follower 免等待获锁、Row Cache 减少 B-tree 遍历）；参数 `hotspot`/`hotspot_update_max_wait_time=100us`/`hotspot_lock_type`，前提"已开启 Binlog"+ 5.7 需关 `rds_ic_reduce_hint_enable`；语义件 `COMMIT_ON_SUCCESS/ROLLBACK_ON_FAIL/TARGET_AFFECT_ROW`（8.0 禁 autocommit、`ERROR 7531`）；排队件 Statement Queue 的 hint 顺序要求；分布式版更硬约束（单分片事务、主键/唯一键等值、不支持带 GSI 的表、需 XA + 关 TSO + 关共享 ReadView、`SET GLOBAL` 需新会话）；性能锚点（近 50 倍 + 并发 1 时负收益）；失效清单（分区表、触发器、已用 Statement Queue、会话级关 Binlog、`ON UPDATE CURRENT_TIMESTAMP` 列失效）。
   出题：code（`mysql`：给 `stock` 表与并发扣减请求，写"条件原子扣减 + 三态区分（成功/库存不足/无此行）+ 幂等防重扣 + 释放对称"并断言）；rubric（是否用内核 Hint、灰度与回滚开关、`target_affect_row` 与业务错误码映射、与 GSI 的互斥）。
   judgeKind：`mysql` ＋ `llm-rubric`。
   锚点：【源 S8】【源 S9】【源 S10】【源 S11】＋【推（缓存预扣 + DB 落库的补偿与对账）】。
5. **消费幂等与去重窗口**（`alibaba-consumer-idempotency`）
   要点：重复是设计内事件（重平衡 + 发送超时重试），官方结论是"需要在下游消费逻辑中做好消息幂等去重处理"【源 S3】；两类**不会**重复的情况（消息粒度单条加锁、队列粒度一队列一消费者）要能分开说【源 S3】；PushConsumer 两种禁止写法与"超时后线程仍可能继续处理"【源 S12】；实现层必答：去重键选择（`msgId` vs 业务键 `orderNo+eventType`，前者在跨集群/重投场景不稳定【推】）、去重存储（Redis SETNX+TTL vs DB 唯一索引）、**去重窗口必须 ≥ 重试节奏**（阶梯间隔顶端是 2 小时、超过最大次数后每次间隔都是 2 小时；SimpleConsumer 场景还受 `InvisibleDuration` 支配 → 只设 5 分钟一定会漏）【源 S13】、"处理成功但位点提交失败"必然重做所以状态机要可重入、去重记录与业务写必须同事务（否则回滚后留下"已处理"的假象）。
   出题：code（`redis`：有界窗口幂等消费器——并发双投只生效一次、TTL 到期允许重投、失败可清除重做）；code（`mysql`：唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE` 返回"首次/重复"标记，并断言回滚不留痕）。
   judgeKind：`redis` ＋ `mysql`。
   锚点：【源 S3】【源 S2】【源 S12】【源 S13】＋【推（去重键与窗口算术）】。
6. **削峰填谷与堆积治理**（`alibaba-message-peak-shaving`）
   要点：削峰是官方定位的基础能力——"传统消息中间件仅满足业务的异步化需求，而云消息队列 RocketMQ 版诞生于在线互联网和交易业务场景，除了满足异步能力，还将**削峰填谷作为消息的基础能力**""能够提供**亿级消息堆积能力**，可以在大促等流量峰值场景下抗住流量洪峰，保证下游业务在安全水位内平滑稳定运行"，并自述"初始于阿里巴巴双十一核心链路，广泛应用于物流、购物车、积分等系统"；产品口径的容量与可靠性："存储和计算分离，可独立按需水平扩展""单实例集群最高 **100 万 TPS** 稳定消息收发""同城冗余多可用区 + 数据三副本""消息服务可用性最高 **99.99%**、数据可靠性最高 **99.99999999%**""预留 + 突发弹性，最高可节省一半机器资源"【源 S21】。工程侧：堆积=`MaxOffset−ConsumerOffset`、位点被纠正即消息已删【源 S6】、清理按存储节点粒度且不区分是否消费【源 S7】、超限服务端反向流控 530【源 S2】。
   出题：rubric（大促 30 分钟洪峰的削峰预算表：允许堆积多少（换算成存储时长）、超阈值时上游如何被流控、下游优先消费/可丢弃哪些并留证据、洪峰后的追赶计划与冷读风险）；code（`mysql`：给 offset 快照表算每组堆积、追赶速率、预计清空时间与 SLA 违约标记）。
   judgeKind：`llm-rubric` ＋ `mysql`。
   锚点：【源 S21】【源 S6】【源 S7】【源 S2】＋【推（水位与降级编排）】。
7. **消费重试与死信：谁在决定重复次数**（`alibaba-consume-retry-dlq`）
   要点：五状态机（Ready/Inflight/WaitingRetry/Commit/DLQ）；普通消息阶梯间隔（10s、30s、1min、2min、3min、4min、5min、6min、7min、8min、9min、10min、20min、30min、1h、2h）且"若重试次数超过 16 次，后面每次重试间隔都为 2 小时"，而**最大重试次数由消费者分组创建时的元数据控制、支持自定义**；"重试次数 3 → 最多投递 4 次（1 原始 + 3 重试）"；顺序消息为固定间隔；SimpleConsumer 用 `InvisibleDuration` 预估且"重试间隔 = 不可见时长 − 实际处理时长"、修改需"未超时 + 未提交状态"；两条官方建议是"合理重试，避免因限流等诉求触发消费重试"（错误示例：消费速度过高触发限流就返回消费失败等下次重消费；正确示例：延迟获取消息稍后再消费）与"合理控制重试次数，避免无限重试：通过减少重试次数 + 延长重试间隔来降低系统压力"；重试三要素是"状态管理、间隔控制、次数上限"，且"消费耗时的最大上限受服务端系统参数控制，一般不应该超过上限时间"【源 S13】。
   出题：code（`nextDeliverTime(retryCount, isOrderly, invisibleMs, costMs)`，断言阶梯/固定、次数与投递数关系、间隔退化边界）；rubric（毒丸消息的隔离与人工重放，含死信后的业务指标口径）。
   judgeKind：`java-junit` ＋ `llm-rubric`。
   锚点：【源 S13】＋【推（毒丸隔离、死信处置流程）】。
8. **顺序消息的适用边界**（`alibaba-order-message-boundary`）
   要点：顺序由**消息组（MessageGroup）**判定——"相同消息组的多条消息之间遵循先进先出，不同消息组、无消息组的消息之间不涉及顺序性"；生产顺序性两个硬条件——**单一生产者 + 串行发送**（"不同生产者分布在不同的系统……无法判定先后"、"多线程并行发送则无法判定先后"）；服务端存储语义——"相同消息组的消息按先后顺序存储在同一个队列；**不同消息组的消息可以混合在同一队列中，且不保证连续**"；分组可"按照业务逻辑做细粒度拆分，在满足业务局部顺序的前提下提高并行度和吞吐"；典型场景是撮合交易与"数据库变更增量同步（binlog → 下游搜索系统按序还原）"【源 S14】。消费侧的隐藏前提：**顺序处理要求遵循同步提交原则，业务自定义异步分发就无法保证顺序**【源 S12】；分配粒度上"5.0 SDK 是消息粒度、更均衡，早期版本是队列维度"，两者与顺序消费的串行要求如何共存要能解释【源 S3】。
   出题：rubric（库存变更 + 订单状态双写下：哪些事件必须同组、分组键怎么选、消费者扩容时顺序怎么保、失败重试与顺序的冲突）；code（`java-junit`：给定消息与 groupKey 断言"同组不交叉、不同组可混排、扩容后组不重排"的分配器性质）。
   judgeKind：`llm-rubric` ＋ `java-junit`。
   锚点：【源 S14】【源 S12】【源 S3】＋【推（分组键设计与扩容重排）】。
9. **限流：维度、通过策略与集群退化**（`alibaba-flow-control`）
   要点：两个 grade（QPS / 并发线程数；线程数"只统计不管理线程池"）；三种 controlBehavior（直接拒绝、冷启动 Warm-Up、匀速排队=漏桶且官方场景是消息队列式间隔突发）；按调用方（`limitApp` 与优先级 `{origin} > other > default`）与按链路入口（`machine-root`）；热点参数限流（LRU + 令牌桶、商品/用户 ID 例子、仅对含该参数的调用生效）；集群限流（Token Server/Client、全局唯一规则 ID、**连接/通信失败退化到本地单机阈值**并可配置）。
   出题：code（组合决策函数：Warm-Up 曲线 + 漏桶排队上限拒绝 + 集群退化开关 + 按 origin 区分阈值，断言优先级与退化行为）；code（`redis`：跨实例共享令牌桶，桶服务不可用时按"单机阈值 × 实例数"上限拒）。
   judgeKind：`java-junit` ＋ `redis`。
   锚点：【源 S16】【源 S20】【源 S19】＋【推（阈值推导与双级降级的容量陷阱）】。
10. **熔断降级与"大盘不红"的监控口径**（`alibaba-circuitbreaker-observability`）

## 5. 出题角度

### 题面草稿 A（`code`，`judgeKind=mysql`）——"扣减 + 幂等 + 对账"三段式
> **库存扣减的正确性（阿里交易风格：先把语义写死，再谈优化）**
> 表：`stock(id INT PRIMARY KEY, kucun INT NOT NULL)`、`dedup(biz_key VARCHAR(64) PRIMARY KEY, order_id BIGINT, created_at DATETIME)`、`order(order_id BIGINT PRIMARY KEY, buyer_id BIGINT, sku_id BIGINT, qty INT, status ENUM('INIT','PAID','CANCELLED'), version INT)`。
> 要求（每条写注释说明它对应哪种真实故障）：
> 1) **原子扣减三态**：实现"扣 `qty` 且库存不得为负"的 SQL，用 `ROW_COUNT()` 判命中，并区分"扣减成功 / 库存不足 / 该行不存在"三态（提示：`WHERE id=? AND kucun >= qty` 只给你两态；说明 `TARGET_AFFECT_ROW 1` 语义下"未命中记录"为什么会失败，MySQL 侧如何补齐第三态）；
> 2) **幂等防重扣**：同一 `biz_key` 重复请求只能扣一次，并输出 `is_duplicate` 标记列；去重记录必须与扣减在**同一事务**内（断言：扣减回滚后去重表不得残留记录）；
> 3) **热点退化检测**：给定 200 行 `concurrent_deduct_trace(ts, order_id, sku_id, latency_ms, result)`，输出每个 SKU 在 1 秒窗口内的最大并发扣减数、P99 延迟、失败率，并标出 `HOTSPOT_RISK`（阈值自定并说明依据，题面不预设）；
> 4) **对账**：找出"已扣库存但订单未进终态"与"订单 PAID 但无扣减记录"两类差异；重复扣减必须按"次数 ≠ 1"判定，不是"有没有"；
> 5) **回滚对称**：给一条 `CANCELLED` 订单实现"释放库存"，且与扣减幂等对称（同一 `biz_key` 的释放只能生效一次）。
> 用例：并发双投、库存恰好为 0、`qty` 大于剩余、行不存在、扣减后事务回滚、取消单二次释放、同一订单被扣两次。
> 区分度：**三态区分、去重与扣减同事务、释放的对称性**——任一处缺失即可判定只写过 Demo。

### 题面草稿 B（`rubric`，10 分制，主推）
> **你正在面试阿里巴巴某交易团队的 Senior Backend（大促稳定性方向），45 分钟**
> 约束（全部可在公开文档核查，不要质疑出处）：① 单热点行更新是**串行**的，官方原话"分库分表策略在性能提升方面并不会有太大帮助"；② 消息投递不是 exactly-once，重平衡与发送超时重试会造成**少量重复**，官方要求下游做幂等去重；③ 消息按**存储节点粒度的存储时长**清理、不区分是否消费，超过即不可回溯；④ 消费重试的阶梯间隔顶端是 **2 小时**（超过 16 次后每次间隔都是 2 小时），最大重试次数由消费者分组元数据控制、可自定义，重试次数 N 意味着最多投递 N+1 次；⑤ 定时消息是毫秒时间戳、默认最长 **24 小时且不可自定义**；⑥ 堆积/存储压力过高时**服务端会反向流控**（`530 TOO_MANY_REQUESTS` + 客户端指数退避）；⑦ 集群限流在 Token Server 连接/通信失败时**退化到单机阈值**；⑧ 熔断的异常统计**不含 BlockException**；⑨ 系统自适应保护用 `maxQps × minRt` 估容量、Load 参考值 `CPU cores × 2.5`、且仅对入口流量生效；⑩ 只读实例/RO 默认只有**会话一致性**，读不到 RW 最新值。
> 请给出：① 一次"秒杀下单"的**一致性方案矩阵**（每一步选本地事务/事务消息/Seata 哪种模式/只记录不保证，并写清失败由谁补偿）；② 库存的**三层设计**（缓存预扣 → DB 条件更新 → 对账），是否使用 `COMMIT_ON_SUCCESS/TARGET_AFFECT_ROW`、Statement Queue 或 `hotspot` 内核优化，各自的失效边界、灰度与回滚开关，以及"如果这张表要加 GSI 怎么办"；③ **削峰预算表**：允许堆积多少（换算到存储时长）、超阈值时上游被流控后的连锁、下游优先消费哪些消息、哪些可以直接丢弃且如何留证据、洪峰后的追赶计划与冷读风险；④ 一次故障演练脚本：把"返回 FAILURE"当成限流手段从而引发大量重试的复现 → 用"最大重试次数 + 延迟拉取 + 毒丸隔离 + 死信处置"四层修复；⑤ 限流/熔断/自适应保护的**联合阈值表**（写出彼此大小关系与为什么，给低峰与高峰两套数）＋"降级触发率"如何进 SLO；⑥ 大促前一次滚动发布的**无损预案**（下线顺序、预热 120 秒的依据、无 header 入口的灰度标签处理、回滚判据）；⑦ 一个你**主动关掉**的能力（AT 全局锁 / 集群限流 / GSI 任选）并说明代价。
> **加分点**：讲清"事务消息保证最终一致，而不是不丢不重"，并给对账口径；指出幂等窗口必须 ≥ 最长重试跨度（默认 2 小时）而不是随手设 5 分钟【与④呼应】；用官方数据说明热点行优化在低并发下的**负收益**并给压测判据；说明 AT 全局锁与库存热点行的冲突（等待从行锁搬到 TC 层）；把 `ConsumerOffset < MinOffset` 被强制纠正当作**静默丢消息**的质量指标监控；点出集群限流退化时"单机阈值 × 实例数 > 期望总阈值"的容量陷阱【源 S19】；解释"限流异常不计入业务异常，所以大盘不会红"并要求两条曲线【源 S17】；给出预热窗口与 JIT/连接池到达稳态时间的实测方法【源 S24】；指出 GSI 的 XA 多写放大，以及"PolarDB-X 热点更新不支持带全局索引的表"这一**互斥**【源 S11/S28】；说明关闭共享 ReadView 会让部分查询变慢的连带影响【源 S11】；⑦ 真的关掉了一件并给量化代价。
> **不足点**：全程不提幂等；把 MQ 当 exactly-once；"削峰就是加机器"；重试次数写"3 次比较稳"而无理由；熔断只说"短路掉"；答不出限流退化的方向；把 `WHERE kucun > 0` 当成防超卖的全部；给不出任一可测判据（QPS/RT/堆积/位点/延迟）；引用"双 11 官方数字"（见 §7 第 1 条）。

### 题面草稿 C（`rubric`，短题，10 分钟）
> "订单服务写完库、半消息也发出去了，接口返回成功。30 秒后：购物车侧读到的是旧状态；履约侧完全没收到消息。给你三条现场线索——服务端出现 530 错误码、消费者组堆积持续增长、某队列的 `ConsumerOffset` 突然等于 `MinOffset`。请说明这三个现象各自最可能的机制，以及你的前三个动作。"
