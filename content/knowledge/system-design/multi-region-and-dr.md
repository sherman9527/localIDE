# 多区域、容灾与容量：把"高可用"落到可验证的数字上

对应考点：`multi-region-dr`、`partitioning-routing`、`capacity-estimation`、`observability-slo`、`safe-rollout`、`cost-ownership`
适配难度：principal 优先（senior 需能答到 60%）｜出题形式：`rubric` + `code`（mysql/redis 局部）

---

## 1. 核心机制

### 1.1 先定义"什么不能坏"
- 可用性目标要写成 **SLI 公式**：`成功率 = 非 5xx 且延迟 < SLO 阈值的请求 / 总请求`，来源必须是边缘/客户端，而不是应用日志。
- Error budget 决定发布节奏：`budget = (1 - SLO) × 月度请求量`；预算烧完自动冻结特性发布，只允许修复类变更。写不出这条的团队，"高可用"只是口号。
- RPO/RTO 由业务与法务给出，不由工程师拍：金融/健康数据 RPO≈0；营销推荐可 RPO=小时。RTO 的真实构成 = 检测 + 决策 + 切流生效 + 客户端收敛 + 数据追赶，**DNS TTL 与客户端连接池/keep-alive 常常是最大项**（移动端更糟：HTTP/2 长连接 + 本地 DNS 缓存，切换可拖到几十分钟）。

### 1.2 三种多区域形态与代价
| 形态 | 写路径 | 一致性 | 典型用途 | 关键坑 |
|---|---|---|---|---|
| 主动-被动（DR only） | 单区写，跨区复制 | 复制延迟决定 RPO | 合规要求"数据主区域"（中国大陆/欧盟） | 备份从未真恢复过；切换脚本腐化 |
| 读副本就近 + 单写区 | 写回主区 | 会话内读己之写可用版本门禁解决 | 全球化 SaaS、移动后端 | 写请求跨区 RTT 抬高 p99；主区故障要"选主 + 客户端刷新" |
| 单元化（cell / shard-per-region） | 按用户/租户固定归属单元，单元内自包含 | 单元内强一致，跨单元异步 | 超大规模（社交、支付、Apple 式"用户数据归属"） | 单元迁移、热点单元、跨单元查询（好友/搜索）要专门服务 |
- 跨区"多主同时接受写"必须回答冲突：LWW 丢并发编辑、CRDT 只适合计数/集合/文本、业务级 merge 最贵但最正确。面试要点："哪些字段允许丢、哪些绝对不能丢"。

### 1.3 数据面容灾
- 对象存储：跨区域复制（异步，分钟级 RPO）+ 版本控制 + Object Lock（合规不可变）；快照/备份要**加密密钥分区**——密钥不可用时备份等于没有。
- 湖仓：Iceberg 元数据 + 数据文件跨区复制要**成对复制**（快照一致性靠 metadata 指针）；v3 的 row lineage（1.10.0 起，2025）让"哪些行属于哪次提交"可追溯，跨区校验与增量同步变可行；Paimon 主键表的 changelog/快照跨区复制同样需核实兼容性（多引擎读写细节 需核实）。
- PITR 的正确姿势：全量快照 + 连续 WAL/事务日志归档 + **恢复演练**（每周把最近一次 PITR 恢复到隔离环境跑断言）。没演练过的 PITR 不算能力。
- 数据库：多数派写（Raft/Paxos）跨区会带来写延迟（跨区 RTT 直接进 p99）；解法：quorum 拓扑（3 区 2/3 但写只在同区多数派 + 跨区异步），或单元化避免跨区共识。

### 1.4 切流与流量层
- 切流是**四层动作**：DNS/GSLB → 边缘/网关路由表 → 服务发现 → 客户端配置刷新。每层都有生效延迟，要分别给 TTL 和"强制过期"手段（如返回 421/`Connection: close`、下发配置版本号）。
- 容量前提：切流前必须回答"存活区域能不能吃下 100% 流量"，包括**下游依赖配额**（第三方短信/支付渠道、模型推理配额）——这类配额是隐性单点。
- 有状态组件的切换：Redis 集群（跨区复制最终一致，切换会丢写）、Kafka（MirrorMaker 双向同步的循环复制/offset 映射、以及消费组位点翻译）——这些是 principal 才答得清的细节。

### 1.5 容量估算的可验证形式
- 链条：DAU → 人均动作 → 日事件量 → 平均字节 → 日增字节 → 副本 × 索引/压缩系数 × compaction 放大 × 保留期 → 存储；峰值 = 日均 × 峰谷比 ×（发布/大促/时区叠加）系数。
- 计算：QPS → 单实例吞吐（实测，不是"官方支持"）→ 冗余策略（N+2 跨 AZ，还是 2N 双区）。
- 关键区分能力：**说清不确定性在哪**（"事件字节数按 p50 还是 p90 估"、"egress 是否计费"），并给出验证实验（压测点、灰度对照、成本报表对账）。
- 2026 现实：成本单元要能落到 `$/请求`、`$/GB 查询`、`$/千 token`；湖仓 + OLAP 双引擎读同一份表时，收益与重复计算成本要一起算。

### 1.6 可观测性与演练
- 三信号 + 第四信号（profiles）：OpenTelemetry Profiles 2026-03 进入公开 alpha，连续 profiling 已可试点；exemplars 把 p99 断链跳到具体 trace；日志要"结构化 + 低基数"，高基数分析放列式后端（ClickHouse/Doris）而不是塞进 Prometheus label 或 ES mapping。
- SLO 多窗口告警（fast burn 6h/5m、slow burn 3d/6h）替代"CPU>80%"式无效告警；错误预算燃尽率作为发布闸。
- 演练类型：区域级（kill region）、依赖级（第三方 503/超时）、数据级（恢复到隔离环境并断言）、切流级（真实拨测）。演练要有"失败即修"的跟踪闭环，否则形同表演。
- 拓扑盲点：客户端侧真实首屏/成功率（RUM）、推送到达率、端上崩溃率——Apple 场景尤其需要"端上指标 → 云端 SLI"的映射链路。

## 2. senior / principal 会被追问什么

1. "你的 SLO 数字是多少？SLI 从哪采？谁为超支负责？"
2. "区域整片挂，用户多久恢复？把每一段延迟（检测/决策/DNS/客户端/数据追赶）报出来。"
3. "跨区写冲突你怎么处理？给我 3 个字段，分别说明允许丢、不允许丢、必须 merge。"
4. "Kafka MirrorMaker 双向同步时，消费组位点在切换后怎么对应？"（offset 映射表 / 幂等重放 / 从"切换时间点"开始消费并接受重复）
5. "你怎么验证备份是可用的？"（恢复演练频率 + 断言 + 演练记录；RPO 靠连续性监控而非猜测）
6. "活区吃不下 100% 怎么办？"（降级预案：关掉哪些非核心功能、按优先级切流、队列化、只读模式）
7. "为什么不上多主全局一致（Spanner 式）？"（成本/延迟/复杂度，且业务收益不明显；何时必须：金融不变量、库存不超卖）
8. "容量翻倍要做什么决策？哪些组件会先崩？"（元数据、单表热点、连接数、Kafka 分区、ZK/etcd 会话、第三方配额）
9. "上一次真实故障：从告警到恢复的时间线、你在其中的动作、事后改了哪三条红线？"（principal 必问）

## 3. 常见错误答案

- "双区双活，用户无感知" → 说不清延迟预算和谁付跨区 RTT 的钱。
- "RPO=0" → 多数派写 + 异步备份的组合根本给不出 RPO=0；无法说明验证方式。
- "上 K8s 多集群就高可用" → 忽略存储、DNS、证书、第三方依赖、控制面单点。
- "备份放另一个云就安全" → 恢复网络带宽、密钥可解性、跨云 egress 成本、演练缺失。
- 容量估算只给"服务器数量"，不给峰值倍率、增长率、冗余策略与不确定性区间。
- 把 Prometheus label 当维度分析（基数爆炸），或把全量结构化日志塞 ES（成本失控）。
- 演练只测"服务能不能起"，不测"客户端能不能收敛到新入口"。

## 4. 出题角度

### 题面草稿 A（`rubric`，10 分制）
> **Airbnb · Principal Engineer（50 分钟）**
> 你是某平台的 owner。当前架构：单区域（us-west-2）写，两个只读副本区；MySQL（InnoDB）主从 + Kafka（RF=3，本地 12 个月保留）+ Redis 集群 + 数据湖（S3 + Iceberg，Spark 批处理 + Flink 流处理）+ 面向 C 端的 API 网关（移动客户端占 70%，长连接）。
> 法务要求：欧盟用户数据主存必须在 EU 区；SRE 要求年度可用性 99.95%（当前 99.5%，且历史上 3 次故障中有 2 次是"切流没生效"）；财务要求年度 infra 成本增幅 < 15%。
> 给出目标架构、分阶段迁移计划（每阶段可回滚 + 退出判据）、RPO/RTO 分解表、演练清单、成本模型（含跨区 egress 与重复存储），并明确指出你**不会**做哪些"看起来正确"的事（例如全局多主写）。

**加分点**
1. 用数据说话：把 99.5%→99.95% 拆成"错误预算烧在哪"（变更 / 依赖 / 容量 / 演练缺失），并针对性排优先级。
2. 切流生效延迟分解：DNS TTL、移动 OS 端缓存、HTTP/2 长连接、SDK 配置刷新周期，且给出**强制收敛**手段（`Connection: close`、网关 421、版本化 endpoint）。
3. 合规驱动的区域设计：EU 主存 + 全局元数据不含 PII + 跨区查询用受控复制/匿名化视图；说清哪些查询可跨区、哪些必须在区内完成。
4. 明确"不做全局多主写"，理由：写路径延迟进 p99、冲突语义成本、团队运维能力。
5. Kafka/MirrorMaker 位点映射、消费组切换策略、RF 与保留期在成本上的影响；提及 4.x 分层存储降低本地盘成本 + 长保留的取舍。
6. Iceberg 快照/元数据跨区一致性复制方案（先数据后 metadata 指针；row lineage 用于校验；catalog 跨区高可用），并标注需核实的引擎兼容点。
7. 备份可恢复性：每周自动恢复 + 断言（行数/校验和/业务不变量），RPO 由日志归档连续性监控证明。
8. 分阶段迁移含回滚与退出判据（例如"双写期差异率 < 0.01% 且持续 2 周"）。
9. 成本模型有单位口径（$/请求、$/GB、$/分区）、峰谷系数、并给出至少一个"降本不降 SLO"的具体措施（保留期分级、冷热分层、compaction 调度错峰）。
10. 组织面：on-call 手册、演练排期、依赖团队协议（SLA/配额/接口人）、以及风险登记册。

**不足点**
- 空喊"多活高可用"，无 RPO/RTO 分解、无数字。
- 忽略客户端与网络层收敛（只讲 DNS 一切就好）。
- 把 99.95% 理解为"少点故障"，没有 error budget 治理机制。
- 备份/恢复只字未提演练；对账无自动化。
- 成本只报总盘子，不报单位成本与跨区 egress。
- 迁移计划没有回滚与判据（一步切换式）。

### 题面草稿 B（`code`，`judgeKind=redis`，短平快）
> 给定"跨区只读副本 + 会话版本"模型：客户端每次写返回 `sv`（单调递增版本），Redis 中保存每个用户最近写入版本与各副本已应用版本。
> 要求实现 `read_if_fresh(user, replica_sv) -> HIT|STALE` 与 `record_apply(replica, sv)`，使"读己之写"在副本未追平时返回 `STALE`（测试用注入的复制延迟模拟）。
> 用例：写后立读（STALE→追平后 HIT）、版本回退（拒绝并返回 `OUTDATED`）、并发两会话各自单调（不得互相回退）。

考察：把一致性写成可判定逻辑，而不是名词。

### 题面草稿 C（`code`，`judgeKind=mysql`，容量/正确性小切口）
> 给定 1.2 亿行 `event_log(user_id, ts, payload)`（InnoDB）。写出：
> 1) 深分页 `LIMIT 50 OFFSET 1000000` 的稳定改写（keyset 分页，游标用 `(ts, id)` 复合且需处理同 ts）；
> 2) 按 `user_id` 分片后的"跨分片 Top-N 归并"SQL 思路（可只写单库等价 SQL）；
> 3) 一条识别"重复事件（同 user_id + request_id）"的检测 SQL，并给出可支撑它的索引。
> 用例断言结果集与执行计划要点（判题看结果，必要时看是否用了索引扫描）。
