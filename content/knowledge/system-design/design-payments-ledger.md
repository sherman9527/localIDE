## 1. 核心机制

### 1.1 市场资金流的真实复杂度（为什么不是"调一次支付 API"）
双边市场一次"预订"通常同时发生多条资金流：
1.  guest 一次性付：房费 + 清洁费 + 服务费 + 税（展示口径与法务口径可能不同）；
2.  平台侧：授权（auth）→ 捕获（capture）→ 分账（host 净收入 / 平台佣金 / 供应商）；
3.  结算时点：host 打款通常在**入住后若干小时/天**（Airbnb 的 payout timing 策略）、支持提前打款（Instant Payout，含手续费与额度控制）；
4.  逆向流：取消政策阶梯退款、部分退款、拒付（chargeback，带代表证据包与二次拒付）、押金释放/预授权到期；
5.  跨币种：报价币 / 支付币 / 结算币三口径，汇率取"成交时锁定"还是"结算时市场价"决定谁承担波动；
6.  税务：代扣代缴（VAT/GST/US occupancy tax）、发票要素、报表口径与合规留痕。
- 关键结构性认知：**支付是异步收敛过程**，不是同步 RPC。任何"下单即成功"的实现都会在渠道回调乱序/重复/丢失时崩掉。

### 1.2 账务内核：不可变双分录 + 派生余额
- 表设计：`journal_entry(id, occurred_at, biz_ref, status)` + `journal_line(entry_id, account, direction, amount, currency, rule_code)`；借贷必平（含"在途/挂账"过渡科目做平衡项），余额由流水投影（快照 + 增量）而非直接改字段。
- 不变量必须可自动断言：
  - `Σ(debit) = Σ(credit)` per entry；
  - 任一 `(biz_ref, event_type)` 至多一条生效分录（幂等）；
  - 客账户余额 ≥ 0（除授信白名单）；
  - 平台"在途"科目余额 = 未清算笔数金额和（与渠道文件对得上）。
- 金额一律整数最小货币单位 + 币种（不要 `double`、不要用浮点做分账）；分账尾差用"最大余额法/最后一笔兜底"显式处理。
- 时间三口径：业务发生时间、记账时间（会计期间/日切）、清算时间（对账基准）；日切规则要与渠道清算日对齐，否则跨日订单必然对不上。

### 1.3 状态机与幂等
- 意图（intent）→ 授权 → 捕获 → 清算 → 结算 → 退款/拒付，每步都写"请求幂等键 + 响应快照"，重试返回原响应（并带 `replayed` 标记）。
- 渠道异步通知：接收即落库（原始报文 + 事件 id），处理与落库解耦（可重放、可并行）；同一事件重复/乱序到达要能收敛（按 `event_id` 去重 + 状态机非法转移显式失败并告警）。
- 3DS/SCA（欧盟强制）带来"需额外验证"的中间态：必须建模为可恢复状态而非失败。
- 拒付（chargeback）是**独立生命周期**：一旦进入，商家侧退款不必然消除拒付；要能同时存在"退款成功 + 拒付胜诉"的组合并靠对账纠正为不多退不少退。

### 1.4 对账（真正区分 senior 与背题者的地方）
- 三向对账：内部账 vs PSP/渠道交易明细 vs 银行/清算入账文件；差异分类（缺单/多单/金额不符/状态不符/时间跨日）→ 各自 SLA 与处置动作（自动重放、人工挂账、客资冻结）。
- 迟到容忍：渠道文件可延迟数日、调整项（adjustment/fee reversal）可回溯数月；对账作业必须可重跑（按 `recon_date` 幂等）。
- 长尾：预授权撤销、跨币结算差、汇兑损益科目、失败重试产生的"重复授权"（释放后仍占额度）。
- 资损防线：不平即锁（金额差异超阈值自动暂停该商户/规则出款）；变更需双人 + 影子账（dry-run 跑新旧逻辑对比）。

### 1.5 2025–2026 演进
- 实时清算普及（SEPA Instant、FedNow、UPI；ISO 20022 报文迁移），对账从"日切批"向"分钟级流式对账 + 差额告警"迁移。
- 稳定币/链上结算进入试点：Airbnb 曾宣布试点以加密货币/稳定币向房东出款（合作 Coinbase，时间/范围请**需核实**）；工程含义是"出款通道抽象 + 合规与制裁名单筛查 + 汇率敞口"。
- 欺诈与 AUP：设备指纹 + 行为序列模型 + 图特征（同收款人聚集）；出款前风险评分与限额分层。
- 反洗钱/合规：受益所有人（UBO）、制裁名单（OFAC）匹配、交易监控留痕与可解释性要求（尤其涉及 AI 决策时）。
- 数据面：账务事实来源（ledger）通过 CDC 实时进湖（Iceberg/Paimon 主键表），做经营指标与风控特征，**但绝不允许下游指标反向修改账务事实**。

## 2. senior / principal 会被追问什么

1. "你们账不平过吗？怎么发现的（自动检测还是客诉）？定位链路和最终修复动作？"
2. "渠道回调丢了怎么办？如果回调和主动查询结果冲突呢？"（以查询/清算文件为准，回调只做加速；冲突时按更晚的确定态并留痕）
3. "退款和拒付同时发生，账怎么处理？谁承担？"
4. "分账比例变更怎么灰度？已经发生的历史流水不能改，报表怎么办？"（规则版本化 + 生效时间，报表按事件时间重算，历史不可变）
5. "汇率谁承担？锁汇窗口多长？锁汇失败怎么降级？"
6. "日切与渠道清算日不一致，跨日订单怎么处理？"（在途科目 + 按清算日重算 + 差额科目）
7. "怎么防止一笔预订被扣两次？如果客人被双扣，如何在 30 秒内定位并自动冲正？"
8. "出款熔断条件是什么？（金额差异率、单商户异常增长、制裁名单命中）"
9. "如果让你把同步扣款接口改成异步意图接口，你如何保证调用方（订单系统）用户体验与幂等？"
10. "资金域的权限模型：谁能改分录、谁能触发出款？如何审计与四眼原则？"

## 3. 常见错误答案

- 用 `balance` 字段做加减而无双录流水（无法追溯、无法对账、并发下必丢）。
- 金额用 `double` / `DECIMAL` 但没指定币种与精度，或"元/分"混用。
- 把"渠道返回成功"当作终态，没有清算文件校验；把"HTTP 200"当作业务成功。
- 幂等键用 `order_id` 全局唯一 → 同一订单的"授权"和"退款"互相冲掉（键必须含操作类型/事件 id）。
- 状态用布尔位组合（`is_paid`, `is_refunded`）而非显式状态机 → 出现"已退款且已拒付"的鬼状态。
- 对账写成"每天跑个 SQL diff"，无差异分类、无处置 SLA、无自动重放、无资损熔断。
- 只谈"我们用了 Stripe/Adyen 所以合规没问题"：PSD2/SCA、数据驻留、税务代扣、出款合规筛查都是自有责任。
- 迁移方案是"停机改表"或"新表双写但不对比"。

## 4. 出题角度

### 题面草稿 A（`rubric`，10 分制）
> **Airbnb · Senior/Staff Backend, Payments（45 分钟）**
> 设计"预订资金编排"子系统。规模：日均 120 万笔支付，40+ 币种，3 家 PSP + 银行直连；需求：guest 一次付款、host 入住后 T+1 出款（可选 Instant Payout 收 1% 手续费，且需限额与风控）；取消按阶梯退款；平台佣金在出款时扣；拒付率 0.3%；欧盟 SCA；财务要求"任何时刻能回答：平台账户里应当有多少钱、差异多少、差异来自哪 5 类原因"。
> 请给出：领域模型与账务不变量、支付/退款/拒付状态机、幂等与并发控制、PSP 抽象与故障切换、对账与资损防线、出款风控与熔断、可观测指标与告警阈值、一次"重复扣款"事故的定位与自愈设计，并说明你如何在不停机的前提下把现有"单 PSP 直连"迁到目标架构。

**加分点**
1. 双分录 + 过渡/在途科目显式建模（guest 已付未清算、平台佣金、host 待出款、汇兑损益），并给出可自动断言的不变量清单。
2. 金额处理规范：整数最小单位 + 币种 + 尾差兜底规则（最大余额法），拒绝浮点。
3. 幂等键设计为 `(biz_ref, event_type, event_id)`，重试返回原响应并标记 replayed；非法状态转移与重复请求返回不同错误类别。
4. 异步收敛：回调先落原始报文再处理；主动查询 + 清算文件为终态依据；冲突时按确定态收敛并留痕。
5. 3DS/SCA 中间态、部分捕获、预授权撤销、chargeback 独立生命周期与"退款+拒付并存"的处理。
6. 汇率策略（成交锁汇 vs 结算价）与敞口归属，锁汇失败的降级；分账规则版本化 + 生效时间（历史不可变、报表可重算）。
7. 对账三向 + 差异五分类 + 每类处置 SLA + 自动重放；资损熔断（阈值触发暂停出款/收款）与四眼原则。
8. 出款风控：设备/行为/图特征 + 新收款人冷静期 + 限额分层 + 制裁名单筛查留痕。
9. 可观测：端到端支付成功率（区分技术失败/业务拒绝）、在途余额、对账差异率、回调延迟分布、渠道健康与自动切换指标。
10. 迁移路径分阶段可回滚（影子账双跑 → 双 PSP 分流 → 灰度按商户/币种切流），并给出每阶段退出判据；说明"资金类测试"策略（契约测试、金额不变量测试、故障注入）。

**不足点**
- 无双录/无在途科目，靠 `balance +=`。
- 认为"PSP 保证不重复扣款"。
- 幂等键粒度错误；状态用布尔位组合。
- 无对账差异分类与处置闭环；无熔断。
- 汇率/税务/合规完全未提（在 Airbnb 场景是硬需求）。
- 迁移"一步切换"，无双跑对比与回滚。

### 题面草稿 B（`code`，`judgeKind=mysql`）
> 给定 `journal_entry` / `journal_line`（列名与类型题面给出）：
> 1) 写一条 SQL 找出"借贷不平"的分录（含币种维度：同币种借贷必须相等）；
> 2) 写一条 SQL 计算每个 host 的"待出款余额"，规则：`capture 成功 − refund − chargeback_lost + adjustment`，且必须与 `payout_status <> 'SETTLED'` 关联；
> 3) 写一条"重复扣款"检测 SQL：同一 `(booking_id)` 出现 >1 条 `direction='DEBIT' AND rule_code='GUEST_CHARGE'` 且状态非 `REVERSED` 的记录；
> 4) 给出支撑 (1)(3) 的索引建议。
> 用例给固定数据快照，断言结果集完全一致（含边界：跨币种分录不得被判不平、已冲正记录不算重复）。

### 题面草稿 C（`code`，`judgeKind=redis`，短题）
> 实现"渠道配额故障切换"：`acquire(psp, token_bucket)` 与 `mark_failure(psp, code)`，要求 5xx/超时进入熔断（连续失败 N 次或失败率 > x% 半开探测），限流返回 429 不进入熔断统计（区分"过载"与"故障"），并保证并发下不会双开探测流量。用例注入并发 200、失败序列、时钟推进。
