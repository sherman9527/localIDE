# Agent 评测与回归：从"演示能跑"到"改十次不退化"

对应考点：`agent-evals`、`retrieval-metrics`、`prompt-release`、`agent-test-env`、`agent-product-loop`、`agent-observability`
适配难度：senior / principal｜出题形式：`code`（react-vitest 做指标计算，java-junit 做编排回归状态机）+ `rubric`

---

## 1. 核心机制

### 1.1 三层评测：单步、轨迹、终态
| 层 | 指标 | 抓到的问题 | 典型断言 |
|---|---|---|---|
| 单步 | 工具选择准确率、参数合法率、检索 recall@k / nDCG、拒绝率 | "选错工具 / 参数幻觉 / 检索没捞到" | 与标注 gold 比较（结构化，可自动判） |
| 轨迹 | 步数、重试次数、循环/无进展率、成本、p95 端到端延迟、权限使用面 | "绕远路、重复调用、成本失控、越权尝试" | 轨迹约束（必经步骤、禁止步骤、最大步数）+ trace 断言 |
| 终态 | 任务完成率、答案正确性/忠实度、引用有效率、可执行产物通过率（代码题就真跑测试） | "看起来对但错" | 可验证判据优先（单测通过、数字与查询一致、订单状态真的变了） |
- 判据优先级：**可程序化验证 > 人工/LLM 评审**。能像本系统一样"真跑用例"的（SQL、代码、数据管道），就别用裁判模型。
- `pass@k` vs `pass^k`：`pass@k`（k 次里过一次）衡量能力上限，`pass^k`（k 次全过）衡量**可发布稳定性**；生产 agent 关心后者。

### 1.2 LLM-as-judge 的偏置与治理（说得出偏置名字才算做过）
- 冗长偏好（更长答案得高分）、位置偏好（成对比较时先看第一个）、自我偏好（同家族模型互抬）、格式偏好（markdown 漂亮即高分）、锚定（rubric 顺序/示例分数影响结果）。
- 缓解：固定且细粒度 rubric（每分对应可核对证据）、成对比较 + 顺序双向跑、多裁判（不同家族模型）投票或取中位、分数校准（与人工锚点集回归，报告一致率/kappa）、把裁判 prompt/模型版本锁进评测配置、**定期用人工盲评审计裁判漂移**。
- 裁判也要有测试集：给一批"已知高分/低分"样本，裁判判分与人工判分的相关性/一致率不达标就不允许改裁判版本。

### 1.3 评测集构建与防污染
- 来源：线上真实失败/接管会话（脱敏后）、业务专家构造的边界用例、红队注入与安全用例、性能与成本用例（长上下文、多工具、慢依赖）。分层抽样：高频意图 × 长尾难例。
- 规模：核心回归集小（50–200 条，CI 每次跑，分钟级）、全量集大（夜间/发布前跑）、生产影子集（真实流量双跑）。
- 污染控制：评测样例**不得**进入检索库/记忆/fine-tune 数据；评测集分公开（开发用）与盲测（发布闸用）两套，盲测集定期换题。
- 版本化：数据集 + 判分器 + 环境（模型版本/温度/工具 mock）一起打版本，任何一项变动都要在报告里显式说明，否则"分数变化"不可解释。

### 1.4 回归与发布门禁
- 指标三层看板：质量（完成率/忠实度/引用有效）、运营（成本/延迟/步数/接管率）、安全（注入成功率、越权尝试、策略绕过）。
- 门禁写法（可落地）：`质量分不下降超 X（统计显著）`、`p95 延迟与成本涨幅 < Y%`、`安全用例 0 通过失败`、`新增失败用例必须入库为回归`。
- 统计意识：小样本下 1–2 个百分点是噪声 → 配对比较（同一问题两策略成对跑）、置信区间/符号检验/Bootstrap、多种子重复（温度 > 0 时）；报告里给区间不给裸数。
- 失败分诊：模型能力问题（换模型/改提示）vs 工具问题（描述/错误语义）vs 数据问题（检索缺失/新鲜度）vs 产品定义问题（任务本就模糊）；修复要"改一处，回归一片"。
- 线上闭环：灰度 + 影子双跑（新旧策略同流量对比）、人工修正回流为评测样本、每周失败轨迹评审（把 Top 失败转成用例）。

### 1.5 评测环境（agent 特有的难点）
- 副作用与可重放：mock 工具（契约级）适合单步/轨迹评测；端到端需要沙箱真环境 + 数据快照 + 可回滚（否则"评测跑一遍，测试库脏了"）。
- 录制/回放（record-replay）：把线上一次会话的工具请求/响应录下来回放，实现"确定性重跑 + diff 定位差异"；对无法回放的真实外部动作，用"意图化桩 + 人工确认"。
- 非确定性控制：温度 0 / 固定 seed（若支持）、前缀稳定、外部依赖桩化、时钟注入；把"随机性预算"写进评测配置并在报告中标注重复次数。
- 成本与时间预算：评测集要有成本上限（否则没人愿意跑），大集抽样 + 分层触发（改动影响面决定跑哪个子集）。

## 2. senior / principal 会被追问什么

1. "你上一个 agent 项目的评测集多大？怎么来的？多少条是自动判分？"
2. "分数从 7.6 涨到 8.1，你怎么知道不是噪声？"（配对比较 + 多种子 + 区间；以及盲测集）
3. "裁判模型换了个版本，全线分数涨了 0.5，你怎么办？"（基线漂移：同批样本重跑旧裁判建立映射；发布闸改为"相对基线差值"；人工锚点复核）
4. "怎么发现'线上好了、评测集差了'或反过来？"（分布漂移监控：意图/语言/长度分布、新失败模式聚类；评测集换血节奏）
5. "多 agent 系统的评测怎么做归因？"（每个子 agent 局部指标 + 终态指标；轨迹级"哪一步引入错误"的标注方法，可做自动"反事实重放"：把该步换成 gold 看结果是否变好）
6. "评测成本太高，怎么降？"（分层触发、抽样、缓存桩、离线批、按变更风险选集）
7. "回归测试怎么覆盖安全？"（注入用例库、越权动作断言、外带检测、红队例会）
8. "你如何向上线后仍失败的用例学习？"（失败→用例→修复→验证→发布的闭环时长与 owner）

## 3. 常见错误答案

- 只有"演示 10 个 case 手工看过"。
- 用单一"平均分"，不给分布/区间/成本/延迟；不区分 pass@1 与 pass^k。
- 裁判自由打分（无 rubric、无证据要求）→ 分数不可解释，改动无法归因。
- 评测集与训练/记忆/检索同源（自测自评），甚至把评测题放进知识库。
- 把 LLM 裁判当"绝对真值"，不与人工锚点回归校准。
- 忽略成本与延迟维度（"质量最好"但一次任务 $3、45s）。
- 评测环境不可重放（每次跑数据都变，失败无法复现）。
- 回归只测"能不能出答案"，不测"是否绕过策略/是否越权调用工具"。
- 温度/随机性不记录重复次数，把单次波动当结论。

## 4. 出题角度

### 题面草稿 A（`code`，`judgeKind=react-vitest`）
> 实现指标计算纯函数（TypeScript）：
> 1) `recallAtK(gold: string[], ranked: string[], k)`、`mrr(gold, ranked)`、`ndcgAtK(gold, ranked, k)`（含**并列分数稳定序**、gold 为空时返回 `null` 而非 0）；
> 2) `pairedCompare(aScores: number[], bScores: number[])` → 返回 `{wins, losses, ties, meanDiff, signTestP}`（符号检验精确 p 值，`n<=20` 用精确二项式；ties 不计入分子）；
> 3) `passK(passes: boolean[], k)` → `pass^k` 的无偏估计 `C(s,k)/C(n,k)`（s=成功次数），`n<k` 返回 `null`；
> 4) `aggregate(reports: Report[])` → 按"数据集版本 + 裁判版本"分组，缺任一版本字段则报 `INVALID`（不得静默混算）。
> 用例：并列 rank 的 nDCG 期望值、gold 空、全 tie 的 p=1、`n<k`、跨版本混算必须拒绝、浮点容差（1e-9）。

（考点：指标定义严谨性 + 统计意识，且完全可判分。）

### 题面草稿 B（`code`，`judgeKind=java-junit`）
> 实现回归门禁决策器 `GateResult decide(EvalReport candidate, EvalReport baseline, GatePolicy policy)`：
> 规则：① 核心集质量分显著下降（用配对符号检验 p < policy.alpha 且 meanDiff < -policy.minDelta）→ `BLOCK`；② 安全用例任何一条失败 → `BLOCK`（不看显著性）；③ 成本涨幅 > policy.costCap 或 p95 延迟涨幅 > policy.latencyCap → `REVIEW`；④ 样本量不足（n < policy.minN）或版本字段缺失/不一致 → `INVALID`；⑤ 通过则 `ALLOW`，但新增失败用例数 > 0 时必须返回 `ALLOW_WITH_TODOS` 且携带用例 id 列表。
> 用例覆盖以上 6 个分支 + "质量分升但安全失败"必须 `BLOCK`（优先级）+ "样本不足但分数好看"必须 `INVALID`。

### 题面草稿 C（`rubric`，10 分制）
> **Airbnb · Senior/Principal Engineer, AI Product Engineering（40 分钟）**
> 你负责"客服自助退款/改期 agent"（工具：订单查询、政策检索、退款执行、升级转人工）。上线 3 个月：自助解决率 62%，但出现 4 起"错误退款"（金额超出政策上限）与 1 起疑似注入（用户粘贴一段"系统指令"文本诱导 agent 提前退款）。老板要求"下季度把自助解决率提到 75%，且资金类错误为 0"。
> 请给出：评测体系设计（数据集来源与分层、三层指标与判据、资金正确性的硬判据）、安全评测（注入用例库与越权断言）、发布门禁与灰度（含回滚触发条件）、线上监控与失败闭环（多久进回归集）、裁判方案及其校准（哪些必须真跑而非 LLM 判分）、以及"解决率提升 vs 资金零错误"冲突时的机制化取舍。

**加分点**
1. 把"资金正确性"从 LLM 判分里剥离：退款金额必须来自政策查询 + 确定性校验器（上下限、幂等键、审批阈值），评测用真跑断言（金额/状态/账目分录）。
2. 三层指标齐备（单步工具/轨迹含成本与步数/终态含可验证断言），并区分 `pass@1` 与 `pass^k`（资金类要求 `pass^k`）。
3. 数据集构成有来源与比例（线上失败与接管会话回流、政策边界用例、多语言/多地区、红队注入、长会话），并明确"盲测集 + 定期换题 + 与记忆/检索隔离防污染"。
4. 注入评测具体化：不可信文本包裹规范、指令式内容不得改变动作权限、"高危动作只能由已验证的用户状态触发（订单归属 + 政策匹配）"、以及"用户自称系统/管理员"的拒绝用例族。
5. 门禁可执行：安全/资金用例零失败即硬 BLOCK；质量下降用配对检验 + 最小样本量；成本/延迟 REVIEW；新增失败必须入回归库（带 owner 与时限）。
6. 灰度与回滚：影子双跑 → 按地区/意图 1%→5%→25%；熔断指标（错误退款笔数、注入命中、转人工率异常升高）自动降级到旧策略或纯人工。
7. 裁判治理：rubric 每条对应可核对证据、成对比较双向跑、多裁判 + 人工锚点集一致率门槛、裁判版本锁定与漂移审计。
8. 监控：错误分类占比（模型/工具/数据/政策）、每任务成本与 p95、资金不变量断言（每日对账：agent 退款笔数与金额 vs 政策上限校验重放）。
9. 解决率与安全的取舍机制化：提升解决率的手段按"资金风险等级"排序（先做只读与解释类，再做限额内的自动退款，超阈值永远走人审），并给出预期影响区间。
10. 闭环时效承诺（例：新失败模式 → 用例 → 修复 → 回归通过的 SLA），以及每周失败评审的产出物（用例 + 规则 + 卡口）。

**不足点**
- 让 LLM 判断"金额对不对"、或把退款执行结果当自然语言解析。
- 只有"我们看用户满意度"，无自动判据、无盲测集。
- 无安全用例库（"上线后再看有没有人攻击"）。
- 门禁靠"感觉没变差"；无统计方法、无最小样本量。
- 忽略成本/延迟，或把它们写成"事后再优化"。
- 无回滚触发条件与熔断指标。
- 评测集与线上知识库同源（自测自）。
