# 上下文工程（Context Engineering）：Agent 的"内存管理"

对应考点：`context-engineering`、`agent-memory`、`agent-cost-latency`、`prompt-release`
适配难度：senior / principal｜出题形式：`rubric + llm-rubric` 为主，`code`（react-vitest / redis）做可判分切片

---

## 1. 核心机制

### 1.1 上下文预算表（senior 的答案必须能列出来）
一次调用的上下文由 6 类构成，各自都要有上限与降级顺序：
1. 系统提示 / 角色与策略（含安全规则）——**位置固定、内容稳定**（缓存友好）；
2. 工具定义（名称、描述、JSON schema、few-shot 示例）——工具一多就是隐性大头，需按会话/意图裁剪；
3. 任务状态（计划、已做步骤、待办）——结构化摘要而非全量历史；
4. 长期记忆注入（用户偏好、历史结论）——按相关性 + 时效 + 置信度选 top-k，带来源标注；
5. 检索材料（RAG 证据）——含引用元数据，最该被"压缩/摘要 + 可展开引用"的一层；
6. 对话历史（含工具原始返回）——最早被截断/外置的一层。
降级顺序（谁先被丢弃）必须是显式设计：`工具原始输出 → 旧对话轮次 → 检索材料 → 记忆注入 → 计划细节`，绝不允许"系统规则被挤掉"（安全护栏失效）。

### 1.2 长上下文的三个真实问题
- **上下文腐烂（context rot）**：token 越多，中部信息召回与指令遵循越差（不是"塞满就行"）。做法：关键约束在开头与结尾各放一次（首因/近因）、长材料先摘要 + 保留可展开引用、跨任务改用外置笔记/文件。
- **注意力与位置偏置**：多文档场景下模型偏向先出现/结构靠前的证据；需要打乱顺序做鲁棒性测试、要求"引用具体片段 id"、关键数值走工具计算而非模型复述。
- **KV-cache 与前缀稳定性**：系统段/工具定义段一旦改动（哪怕动态插入时间戳、随机顺序的工具列表），前缀缓存失效，成本与首 token 延迟显著上升。稳定顺序、把易变内容放尾部是明确的工程约束。

### 1.3 压缩、外置与拆分（三种"省上下文"的手法各有代价）
| 手法 | 何时用 | 代价 / 风险 |
|---|---|---|
| Compaction（历史摘要替换原文） | 长会话、多轮工具调用后 | 摘要丢细节；丢"我曾经否决过某方案"导致重复劳动 → 必须保留决策日志与未解决问题清单 |
| 结构化笔记 / 外部记忆文件 | 跨会话、跨任务的稳定事实 | 写入策略错误会长期污染；需要"记忆可撤销 + 溯源" |
| 子 agent 并行探索 | 搜索面大、可分治（多源检索、大范围代码排查） | token/成本翻倍、误差级联、结论冲突需仲裁；子 agent 必须返回结构化摘要 + 证据引用 |
判据：**能靠"检索按需取"解决的不要预载**（just-in-time），能靠工具算出来的不要塞进上下文（数字、长表、聚合结果）。

### 1.4 记忆体系（写入侧比检索侧更重要）
- 三类：工作记忆（当前任务状态，可丢）、情景记忆（发生过什么，带时间戳）、语义记忆（稳定事实/偏好，去时间化）。
- 写入判据：可复用性 × 置信度 × 时效；冲突处理：新证据覆盖需保留旧值 + 版本；同一事实多来源要能给出"为什么信这条"。
- 必做三件事：**去重**（近似重复不新增）、**衰减/淘汰**（LRU + 价值打分）、**删除**（用户删除请求要能级联到向量索引、原文备份与派生摘要——这条与 privacy 强相关）。
- 安全：检索/网页/邮件内容诱导写入长期记忆 = 持久化注入（一次成功，长期生效）。缓解：写入需"来源可信等级 + 显式确认 + 长度/格式约束 + 记忆隔离命名空间"。

## 2. senior / principal 会被追问什么

1. "你的上下文预算具体是多少？各层占比？超了先丢什么？给我一次真实的溢出事件和你改的设计。"
2. "什么时候你会选 500k token 长上下文，什么时候选检索 + 小上下文？"（成本曲线、延迟、质量、可溯源性；"塞得下"≠"用得好"）
3. "压缩后怎么证明没丢关键信息？"（决策日志、未解决问题清单、被否决方案、数值以工具结果形式保留；回归集里加"长会话一致性"用例）
4. "记忆写入的评估指标是什么？"（命中率、召回正确性、过期比例、错误记忆导致的失败率、删除请求完成时延）
5. "怎么防注入型记忆污染？"（来源分级 + 高危动作需确认 + 记忆命名空间 + 定期审计 + 红队用例）
6. "工具多了效果变差你怎么处理？"（意图路由分组工具集、按需暴露、工具重名/近似功能合并、用评测集测工具选择准确率）
7. "缓存与无状态化之后（MCP 2026-07-28），你的编排层需要怎么改？"（状态自己管、前缀稳定、水平扩展与成本可预测）
8. "多 agent 拆分的收益怎么量化？"（对比单 agent 基线的质量/成本/延迟三元组，而不是"感觉更聪明"）

## 3. 常见错误答案

- "把全部文档都塞进上下文，反正支持 1M token"（不知道中部衰减、成本与延迟、无法溯源）。
- 用模型复述数字（应从工具/查询结果原样带出，且格式受 schema 约束）。
- 历史压缩只保留"摘要段落"，丢掉决策与否决记录 → 重复尝试、循环调用同一工具。
- 工具描述写给人看（营销文案），不写清输入约束/失败语义 → 模型误用与无效重试。
- 把"记忆"实现成"所有聊天记录向量化"（无淘汰、无冲突解决、检索噪声爆炸）。
- 每轮动态改系统提示（插入当前时间/随机工具顺序），前缀缓存全废。
- 只报"平均分"，不看 token 分布、p95 延迟、成本/任务与失败类型占比。
- 声称"多 agent 一定更好"，不给出上下文/权限隔离的真实动因。

## 4. 出题角度

### 题面草稿 A（`rubric`，10 分制）
> **Airbnb · Senior/Principal Engineer, AI Platform（35 分钟）**
> 内部"房东运营助手"：一次会话可长达 60 轮，工具 22 个（日历/价格建议/消息/评论/政策检索/数据查询），需要读长文档（政策 PDF、历史工单），还要记住房东长期偏好（"我不接受宠物"）。现状：平均单次调用 48k token、p95 首 token 3.4s、成本 $0.62/会话、人工接管率 23%，且出现"助手忘了我上轮否决过的方案，又建议一次"的投诉。
> 请给出：上下文预算与分层设计、压缩与外置策略、记忆写入/淘汰/删除治理、工具裁剪与描述规范、成本与延迟的工程手段（含缓存）、评测方案（如何证明改完更好）与上线灰度计划；明确你会**牺牲**哪一项指标换取哪一项。

**加分点**
1. 给出具体预算表（各层 token 上限 + 溢出丢弃顺序），并把"安全规则不可被挤出"写成硬约束。
2. 诊断"重复建议"根因是压缩丢失决策日志 → 引入结构化状态（已否决方案 + 理由 + 时间），并要求后续工具调用前做一致性检查。
3. 工具裁剪：按意图分域暴露（每轮 ≤8 个工具）+ 工具描述含"何时用/何时不用/失败语义"，并用评测集量化"工具选择准确率"变化。
4. 数字/列表类输出一律来自查询结果并带 schema 校验（模型不复述数值），引用必须可点开回到原文片段。
5. 记忆治理三件套：写入判据（复用性 × 置信 × 时效）、冲突/版本、删除级联（向量索引 + 派生摘要 + 备份保留期承诺），并有"错误记忆导致的失败率"指标。
6. 成本/延迟手段可量化：前缀稳定化（系统/工具段固定顺序、易变内容后置）、检索材料先摘要后展开、并行子任务上限 + 早停、小模型路由 + 失败回退；给出预估区间与测量方法。
7. 评测：分层（单步工具选择/轨迹/终态）+ 长会话一致性用例 + 成本与时延同步报告；回归集来自线上失败会话回流（含 PII 处理）。
8. 灰度与回滚：影子双跑（新旧策略并跑对比）→ 5% → 25% → 全量；质量分/接管率/成本作为发布闸与熔断条件。
9. 明确取舍：例如"牺牲极端长文档的一次性召回，换取首 token 延迟与成本下降"，并说明哪些场景需要显式回退（长文档审读模式）。
10. 组织面：文档/政策来源的 owner 与更新 SLA（检索新鲜度依赖它）、工具作者的契约测试要求。

**不足点**
- 只有"提示词优化 + 换更大上下文模型"。
- 无预算表、无丢弃顺序。
- 记忆只谈检索不谈写入/淘汰/删除。
- 用模型复述数字（无证据引用）。
- 无评测与灰度（"上线后看反馈"）。
- 不量化成本/延迟，或把它们当事后指标。

### 题面草稿 B（`code`，`judgeKind=react-vitest`）
> 实现纯函数 `assembleContext(input)`（TypeScript），输入含 `systemRules[]`、`tools[]`、`memory[]`、`retrieved[{id, score, tokens, sourceTrusted}]`、`history[{role, tokens, ts}]`、`planState`、`budget`。
> 要求（全部由用例断言）：① 输出 token 总数 ≤ budget；② `systemRules` 与 `planState` 必须完整保留，否则抛 `BudgetError`（不允许静默截断安全规则）；③ 溢出时按丢弃顺序裁剪：`retrieved` 中 `sourceTrusted=false` 优先 → `retrieved` 按 score 升序 → `history` 按时间从旧到新；④ 同一条检索内容不得重复出现（按 id 去重，保留高分）；⑤ 当裁到只剩 3 条检索时，生成"压缩占位符"（形如 `{omitted: n, refs: [...]}`）以便 UI 展示"还有 n 条未注入"；⑥ 结果顺序稳定（同输入同输出，不得依赖 `Date.now()`/随机）。
> 用例：预算刚好/不足/严重不足、含不可信来源、重复 id、history 为空、必须抛 `BudgetError` 的极端。

区分度：能否把"分层 + 丢弃顺序 + 安全约束不可裁"写成确定性逻辑。
