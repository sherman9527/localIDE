# RAG 架构（2026 版）：检索质量、权限、结构化数据与证据链

对应考点：`rag-architecture`、`retrieval-metrics`、`agent-data-interface`、`agent-guardrails`（部分）、`context-engineering`（衔接）
适配难度：senior / principal｜出题形式：`rubric + llm-rubric` 为主，`code`（react-vitest 做检索融合/去重算法，mysql 做 text-to-SQL 结果校验）

---

## 1. 核心机制

### 1.1 检索栈的分层与每一层的失效模式
```
数据源（文档/工单/代码/表/指标） 
  → 解析与切块（结构感知）
  → 索引（倒排/BM25 + 向量 + 标量属性 + 权限标签）
  → 查询理解（改写、扩展、意图分类、元数据推断）
  → 召回（多路并行：关键词 + 向量 + 图/关系扩展）
  → 融合（RRF/加权）+ 权限过滤
  → 粗排 → 精排（rerank / LLM 重排）
  → 证据组装（引用、截断、层级摘要）
  → 生成（受约束：只依据证据；数值走工具）
```
每层的典型失效：解析丢表格结构 → 内容不可检索；切块打碎语义 → 召回碎片；**先过滤后近邻** → 召回塌陷；rerank 只看 top50 → 正确答案根本没进来；权限过滤在生成后做 → 泄密；引用与文本不对应 → 幻觉无法被发现。

### 1.2 切块与表示（"结构感知"是底线）
- 定长切块只适合纯文本；工程上要用**结构边界**（标题层级、段落、代码函数、表格行组、日志事件簇），并保留 `doc_id + section_path + span` 让答案能定位回去。
- 父子/层级检索（small-to-big）：用小块召回（语义聚焦），把父块（上下文完整）注入模型；对政策文档、手册类特别有效。
- 表格与指标：不要用文本化表格丢进向量库；走"表/列语义 + 指标口径 + 示例值"的结构化索引，检索时返回可查询对象（表名/指标 id），数值由查询给出。
- 代码：按符号（函数/类）切块 + 依赖图邻居 + 文档注释；日志/trace：按事件簇（同一请求链路聚合）而不是按行。
- 近重复与噪声：MinHash/SimHash 去重、来源可信度分级、版本冗余（同一政策 5 个版本）必须带生效时间，否则模型会引到过期条款。

### 1.3 混合检索、融合与重排
- 关键词（BM25）负责精确术语/ID/代码符号，向量负责同义与跨语言；融合常用 **RRF**（`score = Σ 1/(k + rank)`，k≈60 量级）——比分数加权稳（两路分数量纲不同）。
- 过滤与近邻的顺序问题：标量过滤（时间/租户/权限）与 ANN 混合执行有精度损失（预过滤后候选不足）；工程解法：分域索引（按租户/权限等级分片）、后置扩召回（放大 `ef/nprobe`）、过滤条件可下推的索引（标签 + 稀疏维度）。
- 重排（cross-encoder / LLM listwise）：只对 top-N（N≈50–100）做，成本与延迟线性；重排模型要与嵌入模型一起版本化，否则"换嵌入不用重排"会让线上排序突变。
- 校准与去冗：MMR/最大边际相关、按来源去重（同文档多块只留最优）、层级摘要替代长块，缓解上下文挤占。

### 1.4 权限与合规（企业 RAG 的第一道生死线）
- **权限必须在检索层，不在提示层**：文档 ACL 元数据 → 查询时按"用户身份 + agent 代表范围"过滤；索引重建要与权限系统事件联动（撤权后多久生效要有 SLA 并可验证）。
- 多租户隔离：物理/逻辑分片；跨租户泄露是 P0（面试里没提这块，基本判定没做过企业级）。
- 引用与可见性一致：返回给用户的引用必须是用户本来能打开的文档（否则引用本身就泄密）；证据面板要能审计（谁问过什么、看到了哪些片段）。
- PII：入库前脱敏/分级；对"按人查询"（HR/客服）走字段级脱敏 + 用途记录。

### 1.5 新鲜度、增量索引与可复现
- 增量：源变更事件（CDC/Kafka）→ 解析/嵌入 → 索引 upsert；关键是**删除与撤权传播**（向量索引里的幽灵文档是常见事故源）。
- 双索引灰度：嵌入模型升级时"新旧索引并跑 + 结果对比 + 按比例切读"，避免一次重建造成质量塌陷；索引版本号写进每条答案的证据元数据（可复现"当时用的是哪版索引"）。
- 评测口径：离线（recall@k/nDCG/MRR + 忠实度/引用正确率）+ 在线（点采率、答案改稿率、追问率、人工接管率）；离线涨、在线不涨通常是"任务定义/入口体验"问题，不是模型问题。
- 延迟与成本预算：查询理解（小模型）+ 召回（<50ms 级）+ 重排（N 次打分）+ 生成（大头）；缓存分层（查询归一化缓存、片段缓存、答案缓存）；高并发看板类走预计算物化，长尾探索走 ad-hoc。

### 1.6 与 agentic 循环的关系（2025-2026 的主流形态）
- 单次 RAG → **agentic retrieval**：模型可多轮检索、改写查询、判断"证据是否充分"（不充分就再查/换源），并显式输出"我还需要什么信息"。
- 与工具计算分工：检索给"依据"，工具/查询给"数字与状态"；数值一律不来自生成（含单位、时区、口径说明）。
- 与结构化数据接合：语义层作为检索目标（先找指标定义，再生成受约束查询），比裸 text-to-SQL 稳得多；对 SQL 结果做"合理性回归"（与已知聚合值对账、量级检查）。

## 2. senior / principal 会被追问什么

1. "为什么我的 RAG 答案总是漏掉关键条款？"（期待：召回诊断流程——gold 是否被捞到（recall）→ 是否进 top-k → 是否被截断 → 是否被引用；不同位置不同解法）
2. "chunk 多大？"（拒接单一数字，答"按内容类型 + 结构 + 评测结果定，且有层级检索"）
3. "嵌入模型换代怎么办？"（双索引、离线对比 + 在线灰度、成本评估、旧索引保留期）
4. "权限怎么保证不泄密？撤权生效时间？"（检索层过滤 + ACL 事件同步 + 定期红队越权用例 + 索引重建 SLA）
5. "表格数据/指标怎么答？"（语义层 + 受约束查询 + 数值原样返回 + 与 BI 交叉对账）
6. "幻觉怎么治？"（引用强制 + 忠实度判定 + 不可回答的显式拒答 + 数值来自工具 + 上线后抽检与失败回流）
7. "向量库选型？"（独立向量库 vs OLAP/湖内置向量 vs 数据库扩展（pgvector 类）；判据是规模、过滤复杂度、一致性要求、运维能力）
8. "RAG 和长上下文/微调怎么选？"（成本与更新频率、可溯源、权限、评测；"知识"用检索，"格式/风格/技能"用微调或提示）
9. "如何度量 RAG 的业务价值？"（不是"回答质量分"，而是解决率/工时/风险拦截数 + 成本）

## 3. 常见错误答案

- "chunk 512 token + top5 + 大模型总结"当作架构（无结构感知、无融合、无重排、无权限、无评测）。
- 只做向量检索（术语/ID/代码/精确匹配场景一塌糊涂）。
- 用分数加权融合两路不同量纲分数，且不归一化。
- 权限过滤写在生成后 / 或"提示里叮嘱模型不要说不该说的"。
- 删文档只删原文不删索引（幽灵文档），撤权无 SLA。
- 引用只给文档名不给片段定位，无法验证（忠实度评估形同虚设）。
- 让模型复述查询结果数字（口径与精度漂移）。
- 嵌入/重排模型随意升级，无离线对比与灰度。
- 只看离线指标，不看线上行为（追问率、改稿率、接管率）。
- 声称"上了 GraphRAG 就好了"：讲不出实体关系抽取成本、更新与一致性代价、适合哪类多跳问题。

## 4. 出题角度

### 题面草稿 A（`code`，`judgeKind=react-vitest`）
> 实现 `fuseAndGround(inputs)`（TypeScript，纯函数）：
> 输入：多路召回结果 `lists: {name, items:[{id, score, acl[], updatedAt}]}[]`、用户身份 `principal: {groups: string[]}`、当前时间 `now`、配置 `{k, halfLifeDays, dedupeSameDoc}`。
> 要求：
> 1) 先做**权限过滤**（`acl` 为空视为公开；用户 groups 与 acl 有交集才可见），不可见项必须完全不出现在输出（且计入 `filteredOut`）；
> 2) RRF 融合（`k` 可配，默认 60）；同 `docId` 去重时保留该文档的最高排名块（`dedupeSameDoc` 开关）；
> 3) 时效加权：`final = rrf * 0.5^(ageDays/halfLifeDays)`，age 用注入的 `now` 计算（禁止读系统时间）；
> 4) 输出前 `k` 项，含 `{id, score(1e-9 容差), reason}`，`reason` 标记来源路与是否命中新鲜度过期警告（age > 365 天）；
> 5) 稳定序：分数完全相同时按 `id` 升序（保证同输入同输出）；
> 6) 无任何候选时返回 `{items: [], status: "NO_EVIDENCE"}`（生成层据此拒答）。
> 用例：跨路同文档、不可见 ACL、半衰期权重影响名次、并列 id 稳定序、空结果。

### 题面草稿 B（`code`，`judgeKind=mysql`）
> 给定语义层三张表：`metric(id, name, definition_json, owner)`、`metric_value(d, dim_key, dim_value, metric_id, num, den)`、`doc_acl(...)`（题面给 DDL）。
> 1) 写出"按月计算某比率指标"的 SQL（要求 **Σnum/Σden**，禁止对月度比率求平均）；
> 2) 写出"检测口径漂移"的 SQL：同一 `metric_id` 在 BI 层与明细层（`fact`）计算结果差异 > 0.5% 的 (metric, d) 列表；
> 3) 给定一段 agent 生成的 SQL，找出其中 3 处问题（缺权限过滤、跨天求和 distinct、时间归属用了 `updated_at` 而非 `event_time`）并改写正确版本（判题按结果集断言）。
> 考点：agent 数据接口的"确定性校验层"该怎么写。

### 题面草稿 C（`rubric`，10 分制）
> **Apple · Senior/Principal Data & ML Engineer（45 分钟）**
> 需求：给内部工程团队做"遥测与故障根因问答"（数据：设备事件明细在湖仓（Iceberg/Paimon，PB 级）、告警与变更历史、服务代码与 Runbook、隐私政策文档）。要求：答案必须给出证据（事件/提交/文档定位）；不得回答任何涉及可识别用户的问题；查询延迟 p95 < 5s（复杂聚合可转异步）；日均 3 万次问答；权限按团队/数据域划分；模型端点受数据驻留限制（部分数据不可出域）。
> 给出：检索与数据分层设计（文档 RAG + 结构化查询 + 指标语义层三条路的分工）、权限与出域控制、证据链与可复现、评测方案与门禁、延迟/成本预算与降级、索引与嵌入的演进机制、以及你会明确拒绝的两个"看起来能提分"的做法。

**加分点**
1. 三条路分工清晰：文档/代码走混合检索（结构感知 + 层级召回），事件明细走受约束查询（时间范围/分区裁剪 + 扫描量上限），指标走语义层（口径与数值原样返回），并说明三者如何在一个 agent 循环里编排（先查口径 → 再查明细 → 最后引用文档解释）。
2. 权限在检索层且与出域策略统一：ACL/数据域标签进索引元数据 + 查询时强制过滤；不可出域数据走"只返回聚合/脱敏视图"或"就近计算，只回结果"；撤权与删除的传播 SLA 可验证（红队越权用例常态化）。
3. 证据链可审计可复现：每条答案带 `snapshot_id/索引版本/嵌入模型版本/文档版本/时间范围`；同一问题重跑能定位差异来源；证据面板与用户可见权限一致。
4. 确定性数值纪律：模型不得复述数字；数值必须来自查询结果且带单位/时区/口径；"证据不足/查询失败"必须显式拒答而不是猜。
5. 评测分层：检索（recall@k/nDCG）+ 忠实度（引用是否支持结论）+ 任务（根因是否命中，用历史事故复盘集做 gold）；有盲测集与污染隔离；发布门禁含安全/权限用例零失败。
6. 延迟与成本：预算分解（理解 < 100ms、召回 < 300ms、重排 N、生成占大头）、并行多路召回、结果缓存（查询归一化 + TTL + 新鲜度分层）、复杂聚合转异步并给中间进展；p95 达标路径清楚。
7. 演进机制：嵌入/重排双索引灰度与回滚；索引增量与删除/去重；来源 owner 与更新 SLA（Runbook 过期治理）。
8. 与既有数据资产复用：湖仓 MV/物化聚合、OLAP 向量索引或独立向量库的取舍（规模、过滤、运维），并给出"何时不值得引入新组件"的判断。
9. 明确拒绝项且理由硬（例如：不做全量文档一次性长上下文喂入；不做无 ACL 的"企业向量库大一统"；不开放自由 text-to-SQL 直连明细；不把用户可控文本当作指令来源）。
10. 组织与运维：值班与失败分诊闭环、每周失败评审、答案质量抽检与人工锚点、成本归因到团队与用途。

**不足点**
- 把所有问题都归为"文档 RAG"（明细与指标数据无法回答，或让模型猜数字）。
- 权限靠提示词叮嘱；无 ACL 索引与红队验证。
- 无证据元数据（无法复现与审计）。
- 无评测（"我们内部试用后感觉不错"）。
- 延迟/成本无分解，复杂查询同步阻塞。
- 嵌入模型升级一把重建、无灰度无回滚。
- 把 GraphRAG/新框架当银弹，无成本与一致性分析。
